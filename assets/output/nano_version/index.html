Simple Agent Lab 的设计思想

这个框架的重点不是把 agent 包成黑盒，而是把每条边界都摊开： 消息、模型、工具、运行环境、评测产物，各自有清楚的位置。 Docker 只是运行后端，executor 只是执行机制，核心 loop 仍然很小。

一句话架构

agent runtime 是一个透明循环：状态里有消息，loop 每轮构造上下文，调用 agent， 执行它请求的工具，把工具结果变回消息。评测系统则在外面包一层： suite 描述任务，backend 决定在哪里跑，store 负责输入输出和轨迹。

State / Message保存历史，不直接等于 OpenAI payload。
Provider Adapter把项目消息投影成某个模型 API。
Tool Executor并发或顺序执行工具调用。
Artifact Storeinput、result、trace 都是 put/get。
Backendlocal process、Docker、remote、k8s 都只是实现。

老板说的 Docker 到底在哪

不是核心 loop

`core.py` 里的 agent loop 不知道 Docker。它只知道 agent、message、state、tool。 这样普通教学 demo、bash agent、多 agent 委托都不需要容器概念。

是 eval backend

Docker 出现在评测层：一个 benchmark instance 可以交给 `LocalDockerBackend` 跑。但同一个 suite 也可以换成 `LocalProcessBackend` 本地调试。

三个最重要的抽象

抽象 它回答的问题 为什么要拆出来
Suite 这个 benchmark 的任务、镜像、gold 隐藏字段是什么？ 避免每个评测都复制一份 launcher。
ContainerBackend 这次 run 到底在哪里执行？ local process、Docker、remote Docker、k8s 可以互换。
ArtifactStore 输入、输出、轨迹这些 bytes 放哪里？ bind mount、HTTP、S3 的差异不污染 suite 和 runner。

Host half / Container half

Host half

运行在调度机。负责选镜像、workdir、shell，准备 agent 可见输入， 并把 gold/private 数据放进单独的 eval input。

Generic runner

运行在本进程或容器里。负责构造 agent、跑 loop、推 trajectory、 写 result。它不关心具体 benchmark 是什么。

Container half

suite 提供的轻量函数：`build_task`、`extract_result`， 可选 `prepare` / `evaluate`。这才是 benchmark 特有逻辑。

def run(agent, task):
    state.record(task_message(task))
    for turn in range(max_turns):
        visible = build_context_view(state)
        output = agent.generate(visible)
        state.record(output)
        if output.tool_calls:
            results = dispatch_tools(output.tool_calls)
            state.record(tool_result_message(results))
        if output.kind == "final":
            break
def run_suite_instance(suite, backend, store):
    visible = suite.task_input(instance)
    store.put("input/instance.json", visible)
    store.put("input/eval.json", suite.eval_inputs(instance))
    spec = RunSpec(
        launch=suite.launch_spec(instance),
        container_module=suite.container_module,
    )
    backend.run(spec, store=store)
