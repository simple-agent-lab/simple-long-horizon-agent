# Goal Loop: Autonomous Continue-Until-Verifiably-Done Primitive

## Context

Addy Osmani's [Loop Engineering](https://addyosmani.com/blog/loop-engineering/) article
identifies the `/goal` primitive as the missing "keep going until verifiably done" layer
in autonomous agent systems. Every other loop-engineering primitive
(skills, MCP, sub-agents, memory) already ships in Simple Agent Lab. The inner ReAct loop
(`core.run`) stops when the model itself decides it is done — there is no automated
"continue" to keep iterating toward a goal, and nothing *independent* verifies that the
work is complete.

`run_goal_loop` fills that gap. It slots into the `workflow/` outer-orchestration seam:
it drives the existing inner loop via `Agent.run` / `Agent.resume` and owns only the stop
condition. It makes no change to `core.py`.

## Decision

### Resume-based continuation

The continuation primitive already exists: `Agent.resume(state, followup)` appends a
`kind="task"` user message to the *existing* `State` and re-drives the loop, so messages
and trace events accumulate across turns. Goal continuation reuses this rather than
starting fresh conversations.

### Pluggable completion authority

Completion is decided by a `CompletionCheck = Callable[[State], CompletionResult]`
(authority is pluggable, not hardcoded). Three implementations ship:

- `model_declared_check` — the agent calls the `update_goal` terminal tool
  (`ToolResult(terminate=True)`) to self-declare its status; the loop reads the
  structured `details` back out of the recorded tool-result sidecar.
- `command_verifier_check(command)` — an objective shell command must exit 0;
  reuses `tools/bash.py:run_bash`.
- `judge_agent_check(judge, objective)` — an independent judge `Agent` returns
  `{"done": true/false, "reason": "..."}` JSON.
- `default_check(verifier=None)` — model-declared, gated by an optional verifier veto:
  the model must declare done; if a verifier is supplied it can override a declared-done
  back to not-done.

### Multi-dimensional budgets

`GoalBudgets(max_turns, token_budget, wall_clock_seconds)` bounds the loop from three
axes. `max_turns` and `token_budget` (cumulative `AssistantMessage.usage.output_tokens`)
surface as `status="budget_exhausted"`. `wall_clock_seconds` is implemented as a composed
abort deadline (the monotonic-deadline pattern from the eval harness) and surfaces as `status="aborted"`.

### Terminal-status model

`GoalStatus` is one of `complete | blocked | budget_exhausted | aborted`:

- `complete` — `check` returned `done=True`.
- `blocked` — the same blocker reason recurs ≥ 3 consecutive turns (the Codex rule).
- `budget_exhausted` — turns or token budget exhausted.
- `aborted` — caller `abort()` returned True or the wall-clock deadline tripped.

### Event-sourced goal state

Each turn appends an append-only `GoalStatusEvent` to `state.events`
(`State.record_event`). `StateSnapshot.apply` ignores `GoalStatusEvent`
(its `isinstance` ladder handles only `MessageEvent` / `ContextCompressionEvent`),
so the events live only in the trace and never enter the model context.
The goal lifecycle is auditable, replay-able, and survives `Agent.resume` across
sessions — no mutable scratchpad is used.

### Audit-grade prompts with untrusted-objective hardening

`_goal_prompt` and `_continuation_prompt` in `goal_loop.py` wrap the caller-supplied
objective inside `<untrusted_objective>` tags with a safety preamble that instructs
the model to treat it as data, not as instructions that can override developer guidance.

The continuation prompt enforces evidence-based verification: derive concrete checkable
requirements from the objective; verify EACH against current-state evidence; do not trust
your own earlier claim of completion.

### Module layout

- `workflow/goal_loop.py` — the loop, types, and prompts (control-flow).
- `workflow/goal_checks.py` — completion checks and `update_goal_tool` (policy).
- Both re-exported from `workflow/__init__.py`.

## Known Limitations

**Self-declaration is not independent verification.** When `default_check()` is used
*without* a verifier (or `model_declared_check` directly), completion is still the model
self-declaring done — it is NOT independent verification. Independence requires the caller
to supply a verifier (`command_verifier_check`, `judge_agent_check`, or a custom
`CompletionCheck`). The name `default_check` reflects the convenience default, not a
security guarantee.

**Token budget is a soft cap.** `token_budget` is checked *after* a turn completes,
so the actual cumulative usage can exceed the budget by up to one full turn's output
tokens. If strict token capping is required, combine the token budget with a conservative
margin or use `wall_clock_seconds` as a secondary backstop.

**`aborted` is ambiguous at the status level.** Both an explicit caller abort
(`abort()` returning True) and a wall-clock deadline tripping (implemented as a composed
`abort`) surface as `status="aborted"`. Callers that need to distinguish timeout from
cancellation must inspect additional context (e.g. check whether `time.monotonic()`
exceeded the expected deadline) because `GoalResult.status` alone does not carry the
distinction.

## Consequences

- Autonomous multi-turn agents can be driven toward a goal without manual "continue"
  prompting; the loop does it.
- Completion authority is externalized from the model: any objective criterion (a shell
  command, a test suite, an independent judge agent) can gate completion.
- The whole goal lifecycle is auditable: `state.events` contains every `GoalStatusEvent`,
  with `status`, `turns_used`, `tokens_used`, `objective`, and `reason` on each.
- The inner `core.py` ReAct loop is untouched; `run_goal_loop` is pure outer
  orchestration, fully composable with the other `workflow/` primitives.

## Alternatives Considered

- **Native `Stop` / `PRE_FINAL` hook inside `core.py`.** Would let the goal check run
  after each model turn without a wrapper layer. Deferred: `Agent.resume` already gives
  us the right semantic; a native hook is the recorded future evolution, not this task.
- **Mutable `state.data` scratchpad for goal state.** More direct, but deliberately
  kept outside the event-sourcing discipline (`state.py:86-91`). Using `GoalStatusEvent`
  instead keeps the goal timeline in the auditable, replay-able log and never pollutes
  the model context.
- **LLM grades itself (the `run_reflection` pattern).** `run_reflection` uses an LLM
  `APPROVED` marker as its stop condition — the same anti-pattern the goal loop is
  designed to avoid. Pluggable `CompletionCheck` makes independent authority the design
  center rather than the exception.
