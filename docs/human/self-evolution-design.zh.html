自进化机制 · 设计评审

Simple Agent Lab · 2026-06 · 分支 claude/self-evolving-mechanism-jvy0q1（PR #30）· 本页是整轮设计讨论的自包含整理，供团队评审；规范文本以 docs/design/ 下两份英文文档为准。

一段话讲完整个设计：agent 的行为是一个目录（bundle）；进化是提出一个新目录（update）； 证据是跑两遍比一比（gate）；历史是一本只追加的决策日志（decision log）。 所有聪明都在进化 agent 和 update 函数里，所有保证都在确定性基座里。 研究员不需要学这些名词——用户面是 verl/slime 式的三个普通函数（§4）。 当前状态：设计文档两份 + 骨架代码 + Lab 用户面已合入分支（11 个测试全过，demo 可跑）； 首轮评审的两条反馈已处理（§9）。

1 · 目标与定位

目标：在本仓库上构建一个自进化闭环——离线数据管线生产经验，在线（训练与免训练两轨） 消费经验改进 agent。扫完市场后的定位判断：

不做最强的优化器，做唯一可审计的自进化基座。 GEPA 只管 prompt、Agent Lightning 只管权重、Mem0 只管记忆——没有人提供 “所有进化产物（lesson / skill / prompt / checkpoint）走同一条证据链、同一道晋升门”的底座。 每个变更必须能回答：基于什么证据、对比了什么、为什么接受、怎么撤销。 这与仓库既有 ADR（treat-self-evolution-as-harness-capability）的精神完全一致。

2 · 设计是如何收敛的（讨论史）

方案经历了五次关键转折，每一次都改变了架构形态——评审时了解“为什么不是更简单/更复杂的版本”：

阶段方案形态被推翻的原因
v1九阶段路线图：离线管线 + 记忆/playbook/技能/提示词四条免训练轨 + SFT/DPO/RL 训练轨 太大，survey 病——把领域里每个好想法都排进了计划
v2砍成最小闭环：收集 → 蒸馏 lesson → 注入 → 对比 太像 ETL：蒸馏 prompt 写死，永远只产 lesson，没有“agent 在决策”
v3双层：确定性基座（gate/日志/归档）+ 进化 agent（自主选干预手段） 方向确立；读 HyperAgents（DGM-H）后补强 meta 层与 archive 优先级
v4统一训练轨：参考 slime 提出 bundle + 五平面 + 双时间尺度 平面病——五个平面是给论文看的，不是给代码看的
v5方案 A（库优先）：三名词两动词，B（服务化）/C（种群搜索）为兼容的生长方向 首轮评审两条反馈：① Path-based 缺分布式扩展性；② 六个名词对研究员仍太多
v6当前形态：v5 + Lab 用户面——研究员面只剩三个普通函数（verl/slime 式）， 六名词降为机房；分布式立场写入 spec §7.1（内容寻址/append-only 天然可分布，模块边界即存储接缝） —— 当前方案

3 · 文献与竞品：我们吸收了什么

3.1 直接进入设计的研究结论

来源结论落进设计的位置
HyperAgents / DGM-H（Meta FAIR 2026-03） ① 去掉 meta 自改或去掉 archive，增益都≈0；② imp@k 度量 meta agent；③ 它自主发明的 performance tracker / persistent memory 正是我们手工设计的 catalog / decision log meta 候选 kind + imp@k 门禁；“拒绝≠删除”，archive 进 MVP 验收；基座=它刻意固定的外层
ACE（ICLR'26）整体重写导致 context collapse；要逐条增量更新playbook delta 是候选 kind，禁止整体重写
Zombie Agents（2026-02）对抗内容可进入经验库并跨 run 自强化溯源字段必填、staging/promoted 分离、gate 唯一晋升通道、一键回滚
Tinker（Thinking Machines）暴露原语而非 train() 包装；方法放 cookbook核心 API 永远只有两个动词；所有策略是 cookbook 函数
slime（THUDM）train/rollout 靠 data buffer 解耦；同步/异步训练=一个“慢 update 函数”；内环不设门禁、外环必须过门禁
ShinkaEvolve（Sakana）bandit 调度 + 新颖性拒绝省评测预算gate 前免费查重（已实现哈希级）；hit_rate 作为 bandit 先验面
DSPy×MLflow / Prime Intellect父子 run 谱系；环境作为可 pin 的版本化模块decision log 父子引用结构；EvalSlice 带 suite 版本 pin + 切片哈希
EvolveR / Decocted Experience / JitRL存蒸馏后的 lesson 而非原始轨迹；结果计数反馈lesson 候选 kind 的形态与 helpful/harmful 计数
SAGE / SkillRL / Skills-in-the-wild技能库有效但描述过触发会回退skill 候选必须过非目标切片守卫

3.2 竞品地图与“集成而非竞争”策略

赛道代表策略
自进化框架EvoAgentX、AgentEvolver、DGM-H（研究代码）差异化：可审计证据链是它们共同的空白

4 · 核心架构：用户面三个函数，机房六个构件

对标 verl / slime 的集成模型（verl 接自定义 reward = 写一个 compute_score() 函数； slime 接自定义 rollout = --rollout-function-path 指一个函数）：研究员只面对三个概念， 全部是普通函数；bundle / gate / decision log / catalog 这些名词是机房，不出现在用户代码里。

# 研究员需要学的全部（已实现，scripts/run_evolution_demo.py 可跑）：
lab = Lab(workspace, rollout=...)            # ① 跑什么（容器 suite 或任意函数）

def my_reward(run_dir) -> float: ...        # ② 怎么打分（可省略=读 result.json，verl 式）

def my_strategy(ctx): ...                   # ③ 怎么改（可省略=进化 agent 自主决策）
    return ctx.propose(kind="lesson", edits={...}, note=..., evidence=[...])

lab.step(my_strategy)   # 跑→对比→自动晋升/拒绝，返回人话结论
lab.evolve(provider)    # 不写策略：进化 agent 自己诊断、选手段
lab.history()           # 实验史    lab.rollback()  # 回滚

版本管理、证据门禁、审计日志、回滚——全部由框架在 step() 内部强制执行， 策略函数只能提案，无法绕过对比直接生效。整个系统就是下面这一张图： 一个进化循环 + 一条审计底座；想接入什么，找 ⊕ 的位置写一个函数即可：

名词（全是文件，无服务、无注册中心）:
  Bundle   一个目录 = 一个版本的 agent 行为
           （provider.json + prompt.md + playbook.md + lessons.jsonl + skills/）
           内容哈希即版本；“当前版本”是一个指针文件
  Run      一次 rollout 的产物目录（out/result.json + out/trajectory.jsonl，复用现有评测产物）
  Decision log  只追加的 JSONL：每次门禁判定一条，带证据引用

动词（仅有的两个接口）:
  rollout(bundle, instances) -> runs        # 已有：包装 run_dataset()
  update(runs, bundle) -> candidate_bundle  # 唯一扩展点；实现放 cookbook

组合（不是组件）:
  gate    = rollout×2 + 判定 + 记日志        promote = 改一个指针文件
  rollback = 把指针改回去                    archive = 不删目录

五条永不破坏的不变量：

  1. bundle 整体晋升——context 与权重共适应（为 base model 调的 playbook 在 SFT 后可能变累赘），评测/记账/回滚对象永远是 bundle 哈希；
  2. 基座非 agent 化且不可进化——gate、日志、归档、指针是普通代码，任何候选改不到（Zombie-Agents 防线）；
  3. 永不删除——被拒候选保留为踏脚石（DGM-H 消融：没有 archive 增益归零）；
  4. 运行中的 agent 不改自己——meta 晋升下一回合生效；
  5. 核心 API 停在两个动词——反思/GEPA/技能归纳/slime 训练全是 cookbook 里的 update 函数（Tinker 纪律）。

5 · 进化 agent 与双层更新（task / meta）

和固定管线的本质区别：干预空间开放、假设由 agent 提。同一批失败轨迹，这回合可能判断 “是知识缺口，产 lesson”，下回合 lesson 没过 gate，改判“是模式问题，写 SKILL.md”。 固定管线只是这个设计的退化情形（agent 永远选同一种干预）。

进化 agent（普通 Agent，五个工具，权限在工具层强制）:
  query_runs        哪些 instance 在反复失败、成本如何（catalog）
  read_trace        span 树定位失败模式
  read_decisions    过去试过什么、什么有效（hit_rate = bandit 先验）
  write_candidate   只能写 staging；kind=meta 时改自己的 bundle
  run_gate          触发 A/B；唯一的晋升通道（每回合限额）

回合: 观察 → 诊断 → 选干预手段 → 起草 → gate → 解读 → 记日志
晋升: host 侧驱动器读 decision log 后移指针 —— agent 拿不到 promote
任务回合（稳态）元回合（稀少）
修改对象B_taskB_meta（进化 agent 下一个化身）
门禁判据冻结切片上的 reward/cost 等量度imp@k：k 回合预算内产出的 task agent 提升量
成本2×切片≈2×k×回合成本；影子指针命名空间隔离，评测期间的“晋升”不污染真实谱系
触发每回合命中率衰减 + 周期兜底；一次只晋升一个 meta 候选

自指由不可变性闭合：agent 回合开始装载某哈希的 bundle，回合内不变；改自己只影响下个化身； 不需要 meta-meta——再往上的 gate/日志/选择逻辑是基座，故意永远不可改（DGM-H 划的同一条线）。

6 · 评测抽象：Measure × Criterion

评测不绑死在任务分上——成本、轮数、工具报错率都是合法进化目标：

Measure   量什么: runs -> 命名标量     # reward / cost_tokens / latency / turns / tool_error_rate
Criterion 怎么判: 两组量度 -> Judgment（accepted + 逐维 delta + 人话 reason）

improve("reward")                                  # MVP 默认：质量爬坡
guarded(minimize("cost_tokens", min_gain=0.10),
        guards=[not_worse("reward")])              # 效率回合：质量不降省 10% token

刻意不提供加权求和：约束式判定的每条日志都带可读理由 （“reward 0.34→0.41 达标；tool_error_rate 守卫通过”），加权分数解释不了“为什么”。 非目标回归探针由此降级为一个普通守卫；imp@k 也只是一个以回合为评测单元的 Measure。

9 · 评审反馈与待表态问题

9.0 首轮反馈的处理结果（已落地）

反馈处理落点
“目前都基于 Path，扩展到分布式系统缺乏扩展性” 立场成文：内容寻址 bundle + append-only 日志本就是最易分布的结构（git/OCI/CAS 同款）； 全部 I/O 已收在模块函数后面——模块边界即存储接缝，换后端不改调用方； 只有三个点需要协调原语（指针 CAS / 日志追加 / run 产物位置），其中 run 产物已由 evals 的 ArtifactStore/RemoteDockerBackend 解决。显式 Store 协议刻意推迟到出现第二种后端。 spec §7.1
“BUNDLE/GATE/DECISION LOG/CATALOG/ROLLOUT/COOKBOOK 概念太多，研究员不好上手” 对标 verl 的 compute_score / slime 的 rollout-function-path，用户面收成 Lab + reward 函数 + strategy 函数三个概念；策略只能提案、无法绕过对比； 自定义 reward 同时重定义 ctx.failures 与 gate 度量（同一定义）。六名词降为机房，不出现在用户代码。 spec §3.3 · evolution/lab.py（已实现+测试）

9.1 仍请 reviewer 表态的问题

  1. 定位：“可审计的自进化基座、集成而非竞争”这个定位是否成立？有没有我们漏掉的竞品空白或威胁？
  2. bundle 整体晋升不变量：是否接受“永远不单独晋升一个 lesson/prompt”的代价（候选粒度变粗）换取共适应安全？
  3. 权限边界：晋升放在 host 侧驱动器（agent 无 promote 工具）是否足够，还是需要人工 review 档位（accepted → 待人确认 → promoted）？
  4. 评测抽象：拒绝加权求和、只用“目标+守卫”是否会限制真实需求？默认守卫集（非目标探针、tool_error_rate）哪些应强制？
  5. meta 层节奏：imp@k 的 k 和元回合触发阈值如何起步？是否同意“MVP 后第一个扩展”的排期而不是进 MVP？
  6. 容器注入接缝：prompt/playbook/skills 进容器，倾向扩展通用 in-container AgentSpec 覆盖，还是每个 suite 自行支持？（影响下一增量的形状）
  7. 骨架代码：模块切分、Rollout 依赖注入、decision log schema 有无异议——这三处定型后改动成本最高。
