自我改进机制 · 设计汇报

Simple Agent Lab · 2026-06 · 分支 claude/self-evolving-mechanism-jvy0q1（PR #30）· 这页可以单独评审；代码和详细材料见 §10。

  • 做什么：让 agent 自己改进时，也有版本、对比和回滚。agent 的一个版本就是一个目录（bundle）； 想改进就先生成一个新目录；新旧版本做同题对比（gate），赢了才切过去；每次结果都会写进决策日志。
  • 定位：我们做可审计的自我改进底座，不和优化算法抢活。GEPA、RL 训练器这类东西，都当成一个接入函数来用（§1）。
  • 用户怎么用：研究员只需要学三个普通函数（§2.1）；安全规则固定住，策略怎么写完全开放（§2.5）。
  • 现状：8 个模块已经写完，19 个单测通过，不调模型的 demo 也能跑；核心数据都有类型保护（§5）。
  • 希望评审：请重点看 §9 的 6 个问题。

1 · 目标和定位

目标：让 agent 用自己的运行记录持续改进。先支持经验、技能、提示词这类不训练权重的改法， 后面再接模型权重训练；两类改法都走同一套流程。

定位来自一个空位。GEPA 管 prompt，Agent Lightning 管权重，Mem0 管记忆——各种改进手段都有人做， 但“怎么管这些改进”还缺一层。我们的标准很简单：每次改动都能说清四件事—— 凭什么改 · 跟谁比 · 为什么接受 · 出问题怎么退回去。

2 · 核心设计

2.1 研究员只学三个函数

用法参考 verl 和 slime 的思路：要自定义打分就写一个函数，要自定义 rollout 也只给一个函数。

lab = Lab(workspace, rollout=...)            # ① 跑什么：容器 suite 或任意函数

def my_reward(run) -> float: ...            # ② 怎么算分：可省略，默认读 result.json
    return run.result["resolved"]            #    run 是只读视图，带 result/reward/events/dir

def my_strategy(ctx): ...                   # ③ 怎么改：可省略，让进化 agent 自己决定
    return ctx.propose(kind="lesson", edits={...}, note=..., evidence=[...])

lab.step(my_strategy)   # 跑 → 对比 → 赢了上线，输了留档，返回一句结论
lab.evolve(provider)    # 不写策略：进化 agent 自己诊断、自己选办法
lab.history()           # 实验史    lab.rollback()  # 回滚

框架只守一条：strategy 只能提案。它返回什么都不会直接生效，必须赢过对比才能上线。 所以策略写错了，或者被坏数据带偏了，最多浪费一次评测，不会污染当前版本。

2.2 整体架构：一个循环，一条审计链

2.3 三个名词、两个动作、五条规则

名词（全是文件和目录，没有服务，也没有注册中心）:
  Bundle        一个目录 = agent 的一个版本（provider.json + prompt.md +
                playbook.md + lessons.jsonl + skills/）；内容哈希即版本号，
                "当前用哪版"是一个指针文件
  Run           跑一次任务的产物目录（out/result.json + out/trajectory.jsonl）
  Decision log  只追加的 JSONL：每过一次 gate 记一条，带证据引用

  （Bundle / Run 在代码里也是只读类型视图；类型全景见 §2.4）

动作（对外只有这两个）:
  rollout(bundle, slice, run_id) -> runs    # 每次调用都传入题集切片；守卫切片和 held-out 共用
  update(runs, bundle) -> candidate_bundle  # 主要扩展点；具体做法放 cookbook

组合（无独立实现）:
  gate     = 新旧各测一遍 + 判定 + 记日志（测过的 (bundle,切片) 可复用）
  promote  = 改一个指针文件      rollback = 指针改回去      archive = 目录不删除
  1. bundle 只能整体上线——context 和权重可能互相适配，所以评测、记账、回滚都按整个 bundle 哈希来；
  2. 底座不能自改——gate、日志、指针都是普通代码，候选版本改不到，这是防经验投毒的硬边界；
  3. 历史都保留——DGM-H 的消融显示，删掉历史候选后长期收益会掉光；这轮没用的草稿，后面可能有用；
  4. 运行中不改自己——改自己的提案从下回合才生效；回滚就是把指针改回去；
  5. API 只保留两个动作——反思、GEPA、技能归纳、训练都做成 cookbook 函数，不塞进框架本体。

2.4 核心数据结构

磁盘里的文件是真相，dataclass 只是更好读的视图。目录树里的每样东西，代码里都有对应类型； 框架不会把裸 Path 直接丢给调用方，IDE 补全看到的就是 schema。

工作区布局（默认 .evolution/，所有状态都在文件里，ls 和 cat 就能查）:
  bundles/<hash>/            不可变版本目录；manifest.json 记谱系（哈希不含 manifest）
  pointers/task.json         "当前用哪版" = {"hash": …}；meta.json 也一样；
                             shadow/<ns>/ 是隔离的影子指针（imp@k 评测用）
  runs/<run_id>/<instance>/  执行产物：input/instance.json · out/result.json
                             · out/trajectory.jsonl；run_id 层有 bundle.json 溯源戳
  decisions.jsonl            决策日志，只追加
  episodes/                  进化 agent 的回合轨迹

# ════ 视图：盖在目录上，只读、按需读取；.dir 永远保留给底层操作 ═══════════════

@dataclass(frozen=True)
class Run:                        # 一次 instance 运行，对应 runs/run_id/instance/
    dir: Path                     # 唯一构造参数；下面的属性都是访问时才读文件
    instance_id: str              #   = dir.name
    run_id: str                   #   = 上级目录名
    ref: str                      #   = "run_id/instance_id"，写进日志的引用形式
    ok: bool                      #   有 result.json 吗（没有 = 这次跑挂了）
    result: Mapping[str, Any]     #   套件原始结果，bench 自定义字段全保留
    reward: float | None          #   = result["reward"]，标准键的便捷读法
    bundle: str                   #   这次运行装载的 bundle 哈希（溯源戳）
    def events(self) -> tuple[Mapping, ...]: ...   # 轨迹事件

@dataclass(frozen=True)
class Bundle:                     # agent 的一个版本，对应 bundles/hash/
    dir: Path
    hash: str                     #   内容哈希 = 版本号
    manifest: Manifest
    parent: str | None            #   父版本哈希（谱系）
    def read(self, filename: str) -> str: ...      # 读行为文件，缺省 ""
    def files(self) -> tuple[str, ...]: ...

@dataclass(frozen=True)
class Manifest:                   # 关于内容的元数据，不参与哈希
    level: str                    # "task" | "meta"
    parent: str | None
    producer: str                 # 谁生成的：人 / strategy 函数名 / evolution-agent
    evidence: tuple[str, ...]     # 为什么改：run.ref 或 trace id，绝不写绝对路径
    note: str

# ════ 提案侧：研究员或进化 agent 产出的东西 ═══════════════════════════════

@dataclass(frozen=True)
class Proposal:                   # strategy 的返回值：一个候选改动
    kind: str                                # "lesson" | "skill" | "prompt" | …
    edits: Mapping[str, str | bytes | None]  # 路径 -> 新内容；None = 删除该文件
    note: str
    evidence: tuple[str, ...] = ()
    base: str = ""                           # 从哪个历史版本分叉；"" 表示当前版本
    criterion: Criterion | None = None       # 本提案自带的判据（如效率目标）

@dataclass(frozen=True)
class EpisodeContext:             # strategy 能看到的全部
    runs: tuple[Run, ...]                    # 最近跑出来的结果
    current: Bundle                          # 当前版本
    decisions: tuple[Decision, ...]          # 完整实验史，包括被拒的候选
    reward: RewardFn                         # 和 gate 同一个打分定义
    @property
    def failures(self) -> tuple[Run, ...]: ...     # 得分≤0 的 runs；连续分数自己过滤
    def bundle(self, hash: str) -> Bundle: ...      # 取任意历史版本（含被拒）
    def propose(self, **kw) -> Proposal: ...

# ════ 评测侧：gate 会用到的东西 ══════════════════════════════════════════

@dataclass(frozen=True)
class EvalSlice:                  # 冻结题集 = 一次对比的考卷
    suite: str                    # 带版本 pin，比如 "swebench==0.3.1"
    instances: tuple[Mapping, ...]
    instances_sha: str            # 题集指纹，会写进日志

@dataclass(frozen=True)
class Measure:                    # 量什么：每个 run 取一个数，再汇总
    name: str
    per_run: Callable[[Run], float]          # 从 Run（含 bench 自定字段）取数
    aggregate: Callable[[Sequence[float]], float] = mean   # 聚合方式可换

@dataclass(frozen=True)
class MeasureFrame:               # 一次测量的结果，分两层
    name: str
    value: float                  # 汇总值，写进日志
    per_run: Mapping[str, float]  # instance_id -> 值，给配对统计用

Measurement = Mapping[str, MeasureFrame]     # 多维度：每个 Measure 一项

@dataclass(frozen=True)
class Criterion:                  # 怎么判：两组指标 -> 裁决
    describe: str                 # 写进日志的判定规则说明
    def judge(self, baseline: Measurement,
              candidate: Measurement) -> Judgment: ...

@dataclass(frozen=True)
class Judgment:
    accepted: bool
    deltas: Mapping[str, float]   # 逐维度 候选 - 基线
    reason: str                   # 人能看懂的理由，原样进日志

# ════ 三个扩展点的函数类型 ══════════════════════════════════════════════
RewardFn   = Callable[[Run], float]          # float 只是单目标的便利用法；
                                             # 多维分数：判据按名引用 result 字段（§4）
StrategyFn = Callable[[EpisodeContext], Proposal | None]
Rollout    = Callable[[Bundle, EvalSlice, str], Sequence[Run]]

这些类型连起来，就是整个循环。一次 lab.step() 的类型流向如下。代码里也收在 lab.py 的 step() 一个函数里，按顺序读就是这张图；§2.2 架构图里的每条箭头，在这里都有对应签名。

EpisodeContext(runs, current, decisions)         # 观察：三个存储区的只读快照
  │                                              #   runs/ · pointers/ · decisions.jsonl
  └─ strategy(ctx) ──────────────▶ Proposal      # 提案：edits + base + criterion
       └─ stage_bundle(base, edits) ─▶ Bundle    # 候选：manifest.parent = base.hash
            └─ gate(baseline=当前 Bundle, candidate=候选 Bundle):
                 rollout(Bundle, EvalSlice, id) ─▶ [Run]        # 新旧各一组，测过的可复用
                 Measure(每个 Run) ──汇总────────▶ Measurement   # {name: MeasureFrame}
                 Criterion.judge(基线, 候选) ─────▶ Judgment      # accepted + 可读 reason
            └─ Decision 追加进 decisions.jsonl                   # 终点：见下面的 JSON
                 accepted 且 auto_promote ───────▶ promote()      # 指针指向候选 Bundle

下一回合可以从 EpisodeContext.decisions 读到这条 Decision，循环就接上了

类型之间不直接互相挂对象，跨存储只存引用。Manifest.parent / Proposal.base / Decision.candidate["bundle"] 存的是内容哈希， Decision.runs 和 evidence 存的是相对 ref。这样日志不会绑死在某台机器的路径上， 以后搬目录、换远程存储都还能用。

一条决策日志大概长这样。这是 Decision 的序列化，也就是上图的终点。汇总值写进日志； 每个 instance 的原始值留在 runs 目录里，随时可以重算。

{"id": "gate-000042", "level": "task", "episode": "step-000017", "kind": "skill",
 "baseline":  {"bundle": "ab12…", "measurements": {"reward": 0.34}},
 "candidate": {"bundle": "cd34…", "parent": "ab12…",   # 谱系写进日志，做树分析不用扫 manifest
               "evidence": ["trace:…"], "note": "…", "measurements": {"reward": 0.41}},
 "slice": {"suite": "swebench==0.3.1", "instances_sha": "ef56…", "n": 20},
 "deltas": {"reward": 0.07}, "decision": "accepted",
 "reason": "[improve(reward, min_delta=0)] reward 0.34 -> 0.41 (meets min_delta 0)",
 "runs": {"baseline": "gate-000041-baseline",          # 复用旧测量时，直接引用旧 run
          "candidate": "gate-000042-candidate"}}

查重键是 (candidate, baseline, slice) 三元组。同一个候选，如果基线换了，就是一个新问题； 被拒的候选也要能拿出来重测。持久记录只写相对引用。evidence 一律用 run.ref （run_id/instance_id），不写绝对路径。日志应该比任何一台机器都活得久，这条约定以后补不了。

2.5 哪些固定，哪些开放

自我改进还没有标准答案，所以只固定安全规则，策略都可以换。研究别的搜索方式时，不需要改框架本体。

🔒 固定规则⊕ 开放策略（就五个问题）
版本不可变、内容寻址；日志只追加；上线必须有 gate 证据；历史不删除；底座代码不能自改 跑什么（rollout）· 怎么打分（reward；多维分数 = 判据直接引用 result 字段）· 怎么判（criterion，可逐提案覆盖）· 怎么改（strategy / update；提案里顺带决定 从哪个版本分叉、本次用什么判据、要不要删文件）· 上线要不要人确认（auto_promote）

每个开放点都只需要最小改法。要么传普通函数，要么传构造参数；没有注册表、没有子类、也没有配置文件。

── 跑什么 rollout：任何 (bundle, slice, run_id) -> [Run] 的函数 ──────────────
def my_rollout(bundle, slice_, run_id):
    score = run_my_agent(prompt=bundle.read("prompt.md"))  # 怎么跑随你
    out = ws / "runs" / run_id / "case-1" / "out"; out.mkdir(parents=True)
    (out / "result.json").write_text(json.dumps({"reward": score}))
    return [Run(out.parent)]
# 跑容器评测套件则不用写：rollout=dataset_rollout(suite=…, backend=…, …)

── 怎么算分 reward：一个 Run 进、一个 float 出 ───────────────────────────────
lab = Lab(ws, rollout=…, reward=lambda run: 1.0 if run.result["resolved"] else 0.0)
# 同一个定义用两处：gate 怎么算分，ctx.failures 怎么判断失败

── 多维分数：判据直接按名字引用，引用即注册 ──────────────────────────────────
# result.json 里有 {"reward": …, "compile_ok": …} 就够了，什么都不用注册
lab = Lab(…, criterion=guarded(improve("reward"), [not_worse("compile_ok")]))
# 名字解析顺序：reward → 打分函数；cost_tokens 等内置；其余 → result.json 同名字段

── 怎么判 criterion：全局换，或单次提案自带 ──────────────────────────────────
lab = Lab(…, criterion=paired_improve("reward"))      # 全局换成配对检验
ctx.propose(…, criterion=guarded(minimize("cost_tokens", min_gain=0.10),
                                 [not_worse("reward")]))  # 这次只优化效率

── 改什么 strategy：读失败，提一个改动 ──────────────────────────────────────
def add_lesson(ctx):
    if not ctx.failures: return None
    line = json.dumps({"lesson": "check pytest fixtures first"})
    return ctx.propose(kind="lesson",
        edits={"lessons.jsonl": ctx.current.read("lessons.jsonl") + line + "\n"},
        note="lesson from repeated setup failures",
        evidence=[r.ref for r in ctx.failures])

── 从哪分叉 base：树形搜索只需要这一个参数 ─────────────────────────────────
def branch_from_best_rejected(ctx):
    rejected = [d for d in ctx.decisions if d.decision == "rejected"]
    pick = max(rejected, key=lambda d: d.candidate["measurements"]["reward"])
    base = pick.candidate["bundle"]                    # 被拒候选也可以继续拿来改
    return ctx.propose(kind="prompt", base=base,
        edits={"prompt.md": ctx.bundle(base).read("prompt.md") + " …tweak"},
        note="tune the most promising rejected variant")

── 删除一个文件：用墓碑记录删除 ─────────────────────────────────────────────
ctx.propose(kind="skill", edits={"skills/flaky/SKILL.md": None},
            note="retire over-triggering skill")

── 上线要不要人确认：一个构造参数 ───────────────────────────────────────────
lab = Lab(…, auto_promote=False)           # 人工确认模式：
r = lab.step(s); lab.promote(r.candidate)  #   看过证据再上线；没有 gate 证据的哈希会被拒

默认值只是最便宜的起步方案。当前默认是单谱系爬山、improve("reward")、自动上线；框架并不偏向它。 上面 base 的例子就是最小版树形搜索；不同命名空间各拿一个指针，就能做种群，框架代码不用改。 少用的旋钮沉到了引擎室，不占用户面：自定义聚合方式直接构造 Measure，强制重测调 gate(reuse_runs=False)，元回合触发策略等 imp@k 增量一起来。

3 · 进化 agent：不写 strategy 时由谁决定

它和固定流水线的区别是：改什么由 agent 当场判断。同一批失败轨迹，这回合可能判断为“知识缺口”，于是写 lesson； 如果 lesson 没过 gate，下回合可能改判为“模式问题”，转去写 SKILL.md。固定流水线则永远只会用同一种办法。

五个工具，权限都在工具层卡住:
  query_runs        哪些题目反复失败、成本多少
  read_trace        打开一条轨迹定位失败原因
  read_decisions    之前试过什么、什么有效（hit_rate 可当先验）
  write_candidate   起草候选，只能写进暂存区；base=<哈希> 可从任意历史版本（含被拒的）分叉
  run_gate          触发 A/B，每回合有限额——上线只能走这条路

回合: 观察 → 诊断 → 挑手段 → 起草 → 过 gate → 解读 → 记日志
上线不在 agent 手里: 宿主侧代码读决策日志后切指针
回合轨迹写进 episodes/: 提案动机和判定解读也能审计

进化 agent 自己也是一个 bundle，所以它也能被改进。DGM-H 里去掉这层，收益同样会掉光。 改“改进者”时，用 imp@k 来打分：给候选 k 个回合预算，再和现任比，看谁让任务 agent 提升更多。

任务回合（常态）元回合（稀少）
改谁任务 agent 的 bundle进化 agent 自己的 bundle（下回合生效）
怎么判冻结题集上的 reward / 成本等指标imp@k（用影子指针隔离，不污染真实谱系）
成本题集 ≤2 遍（基线可复用）约 2×k 个回合
何时触发每回合命中率走低 + 周期兜底；一次只上一个 meta 候选

自指问题靠不可变性收住：一个回合内配置不变，改自己只影响下个回合；再往上不做 meta-meta，底座永远不能改。

4 · 评测：先量，再判

Measure 负责量：每个 run 取一个数，再按均值、求和、pass@k 等方式汇总。结果分两层：汇总值写进日志， 每个 instance 的原始值留给配对统计。Criterion 负责判：比较两组指标，给出接受或拒绝，以及一句能看懂的理由。 成本、轮数、报错率都可以成为改进目标。

分数不只限于一个 float。每个 bench 的 result.json 想写什么字段都行，Run.result 会原样保留； “标准 reward 键”只是默认的单目标用法。多维分数的接法更直接：判据按名字引用字段，引用即注册。

# 某代码 bench 产出 {"compile_ok": 1.0, "tests_passed_rate": 0.83, "lint": 7.2}
lab = Lab(…,
    reward=lambda r: r.result["tests_passed_rate"],   # 主目标维度
    criterion=guarded(improve("reward"), [not_worse("compile_ok")]))
# compile_ok 不用注册：判据引用的名字自动解析到 result.json 的同名字段

量纲安全靠切片保证：一个切片固定一个 suite，分数只在同一个 bench 的新旧版本之间比，不跨 bench 比。 LLM rubric 打分也走同一个形状：给单个 run 打 0–10 分的 judge，就是一个 per_run Measure。 判据只看数字，不直接看原始轨迹，这是刻意设计的：裁决理由必须能写成日志里的一句话。

improve("reward")                                  # 默认：质量爬坡
paired_improve("reward")                           # 类似符号检验：逐 instance 配对数净胜场，
                                                   #   "+9/-2" 比 "均值高 0.05" 更抗噪
guarded(minimize("cost_tokens", min_gain=0.10),
        guards=[not_worse("reward")])              # 效率回合：质量不降，token 省 10%

我们故意不提供加权求和。“reward 0.34→0.41 达标；守卫通过”三个月后还能看懂； “综合分 0.73 > 0.68”很难说清到底赢在哪。非目标回归探针因此只是一个普通守卫； imp@k 也只是把“一个回合”当评测单元的 Measure，不需要特殊代码路径。

三个已知缺口（代码内有注释标注）：

  1. 容器注入目前只打通了 provider——prompt / playbook / skills 进容器，还需要在容器内 agent 装配处加一个注入口，下一步做；
  2. imp@k 和元回合调度还没做——影子指针机制已经有了，还差调度逻辑；
  3. 相似度查重和 bandit 调度——计划放在 MVP 之后。

7 · 设计是怎么收敛的（5 次推倒重来）

版本形态为什么被推翻
v1九阶段路线图，四条免训练线 + 三条训练线太贪心，像综述，不像能落地的方案
v2最小闭环：收集 → 从固定 prompt 里蒸馏 lesson → 注入 → 对比本质是 ETL：永远只产 lesson，“自我改进”的味道不够
v3两层：进化 agent 拿主意 + 确定性底座管安全方向定下来；读 DGM-H 后补 meta 层和 archive
v4bundle + 五平面 + 双时间尺度五个平面是画给论文的，写代码用不上
v5库优先：三个名词、两个动作评审反馈：① 裸 Path 不利于以后分布式；② 六个名词上手太重
v6v5 + Lab 用户入口（三个函数）；分布式立场写成文档二轮讨论：① 扩展点全收裸 Path，契约只能靠记；② 搜索策略固定得太死
v7当前形态：全链路强类型视图、每次调用传切片、配对判据、测量复用、任意版本可分叉、安全规则和策略分层（§2.5）——

关于分布式的态度（回应 v5 评审①）：内容寻址 bundle + 只追加日志，本来就很容易分布式化 （和 git 对象 / OCI 层类似，哈希就是对象存储 key）；所有 I/O 都收在三个模块函数后面，换存储后端时不用动调用方。 真正需要协调的只有三处：指针 CAS、日志追加、run 产物位置。显式 Store 协议等第二种后端真的出现时再加。

8 · 外部依据：参考了哪些工作

来源结论落点
HyperAgents / DGM-H（Meta 2026）去掉 meta 自改或 archive，收益几乎归零；用 imp@k 评估 meta agent；评测固定，父代选择要隔离 meta 候选 + imp@k；历史永不删除；任意版本可分叉（机制进底座，选择策略放 playbook）
ACE（ICLR'26）整篇重写 playbook 会冲掉已有积累（context collapse）playbook 只允许逐条 delta
Zombie Agents恶意内容一旦混进经验库，会跨 run 自我强化来源必填 · 只进暂存区 · 上线只能走 gate · 一键回滚
Tinker暴露原语，不要包一个 train()；具体方法放 cookbookAPI 停在两个动作
slimetrain / rollout 用 buffer 解耦训练就是一个慢 update 函数；checkpoint 上线也要过 gate
ShinkaEvolve新颖性查重 + bandit 可以省评测预算gate 前先免费查重（已实现）；hit_rate 留给 bandit 用
DSPy×MLflow / Prime Intellect父子 run 谱系；评测环境可 pin决策日志记谱系；切片带版本 pin + 题集哈希
EvolveR / Decocted / JitRL存蒸馏经验，带正负计数lesson 结构 + helpful/harmful 字段
SAGE / Skills-in-the-wild技能描述过宽会伤无关任务skill 候选必须加测无关切片

竞品策略一句话：不和自我改进框架（EvoAgentX、AgentEvolver）拼算法，做它们缺的可审计底座； prompt 优化器（GEPA）和 RL 训练器（verl / slime / Agent Lightning）都作为 update 函数接进来； 记忆产品（Mem0 / Zep）先不碰；进化式代码优化（AlphaEvolve 系）只借机制。

9 · 想请大家拍板的问题

  1. 定位：“可审计底座 + 优化算法靠集成”这个方向成立吗？有没有漏看的竞品或威胁？
  2. 整体上线：不单独上线一条 lesson / 一个 prompt，而是整个 bundle 一起上线。这样候选会更粗，单项归因更难， 但能保护 context 和权重之间的适配。这个取舍能接受吗？
  3. 权限默认值：人工确认模式已经实现（auto_promote=False 时，accepted 候选要等显式 lab.promote()；没有 gate 证据的哈希一律拒绝）。默认设成“任务候选自动上线，meta 候选人工确认”，可以吗？
  4. 评测抽象：只给“目标 + 守卫”，不做加权求和，会不会卡住真实需求？哪些守卫应该默认强制开 （非目标探针、tool_error_rate）？
  5. meta 层节奏：imp@k 的 k 和触发阈值从多少开始合适？我建议它排在 MVP 后第一个做，原因主要是成本： 每次 meta gate 贵 k 倍，但机制上不需要新东西。这个顺序同意吗？
  6. 容器注入入口：prompt / playbook / skills 进容器，是做一个通用的容器内装配覆盖，还是让各个 suite 自己支持？ 这个决定会影响下一步怎么拆。
