接入一个 bench

向本框架添加一套基于 Docker 的 eval 套件的标准做法。

框架已经替你扛下了那些通用且繁琐的部分：容器的生命周期、Python 引导启动、 运行目录的布局、数据在主机与容器之间的进出、并发控制，以及可在主机侧重入的批处理。 你只需要写两个很小的"半边"并把它们注册进来。你不需要修改 bench 镜像， 也不需要把 agent 拷进镜像——agent 在容器启动时才被安装进去。

一次接入的整体形态

从本质上看，一个 bench 就是两个程序，它们在一个共享的"产物存储"（artifact store）处汇合： 一个是主机半边（host half），负责决定如何启动每个实例、以及如何读取结果； 另一个是容器半边（container half），运行在镜像内部，真正执行任务。 这两边都由你来实现；夹在它们中间的一切，都是框架。

备注：产物存储不一定是远端的

这里的"产物存储"只是一个抽象的字节读写接口，并非必须是远程/对象存储服务。 最常见的实现就是本地磁盘上的一个目录（LocalDirStore），把 input/、 trajectory.jsonl、out/ 这些文件直接落在 run_root 下； 需要时再换成远端 store，套件代码不用改。

主机半边 —— 一个 Suite

  • name 与 container_module —— 标识 + 指向容器半边的点分路径
  • launch_spec(instance) —— 把镜像、工作目录、shell、入口、cap_add 作为数据返回（不要写 if 分支）
  • task_input(instance) —— 在 agent 看到实例前，去掉标准答案字段
  • eval_inputs(instance) —— 为容器半边的 evaluate 钩子暂存金标打分输入（在运行环境内打分），或返回 None 表示在别处打分。暂存金标即是开启该钩子的开关（ADR 0020）——不再有单独的 scorer() 方法
位于 evals/<name>/suite.py · 可以使用重型依赖（datasets、docker）

容器半边 —— 两个函数

  • build_task(instance, *, workdir) —— 把实例转换成 agent 的任务 prompt（一个字符串，或一串 content blocks 以支持多模态——文本 + 图片）。它只负责造 prompt，agent 循环是框架的事。
  • extract_result(workspace, instance, *, context) —— 读取本次运行的产物（如一段 git diff）
  • 可选 prepare(...) —— 运行前的准备，结果以 context 回传
  • 可选 apply_oracle(workspace, instance) —— 落地参考解，用于无模型的自检
  • 可选 agent_spec() / build_agent(...) —— 选择 / 定制 agent
随 wheel 发布于 simple_agent_lab/evals/suites/<name>/ · 只用标准库 + 已安装的运行时

五个步骤

1
写容器半边 必需 — src/simple_agent_lab/evals/suites/<name>/container.py

这是运行在镜像内部的代码。它只能 import 标准库和已安装的 simple_agent_lab 运行时，因为 bench 镜像里没有其它东西。

# build_task：实例 dict -> 模型可见的任务 prompt。
# 可返回 str，或一串 content blocks 以支持多模态（文本 + 图片）。
def build_task(instance, *, workdir):
    return f"修复 {workdir} 中的这个缺陷：\n{instance['problem_statement']}"

# extract_result：读取 agent 对工作区造成的影响（而非它的对话）
# 即便用不到也要声明 *, context —— prepare() 的输出就是通过它到达这里的。
def extract_result(workspace, instance, *, context=None):
    return {"model_patch": git_diff(workspace)}
2
写主机半边 必需 — evals/<name>/suite.py

一个满足 Suite 协议的类。各实例之间的差异（用哪个镜像、仓库在哪、 测试需要什么权限）都以数据的形式写在 launch_spec 里—— 绝不要写成 runner 里的分支判断。

class MyBenchSuite:
    name = "mybench"
    container_module = "simple_agent_lab.evals.suites.mybench.container"

    def launch_spec(self, instance):
        return LaunchSpec(image=instance["image"], workdir="/repo",
                             cap_add=("SYS_PTRACE",))   # 测试所需的权限
    def task_input(self, instance):
        return {k: v for k, v in instance.items() if k != "gold_patch"}
    # 为容器半边的 evaluate 钩子暂存金标（在运行环境内打分，ADR 0020）。
    # 返回 None 表示在别处打分（后续的一次 run，或官方 harness CLI）。
    # 不再有单独的 scorer() 方法。
    def eval_inputs(self, instance):
        return {"expected": instance["gold_patch"]}   # 或 None 表示在别处打分

LaunchSpec 是一个 frozen dataclass——纯粹的启动数据，没有行为。 各实例之间的差异都放在这里，绝不写成 if 分支：

class LaunchSpec:
    image: str                              # 该实例使用的 Docker 镜像
    workdir: str                            # 容器内的工作目录（如 /testbed、/app）
    shell: tuple[str, ...] = ("bash", "-lc")  # 引导脚本被附加到的 argv 前缀
    entrypoint: str | None = None           # ""=清空镜像 ENTRYPOINT；None=保留镜像默认
    platform: str | None = None             # 如 "linux/amd64"
    cap_add: tuple[str, ...] = ()           # 测试所需的 Linux 权限（如 "SYS_PTRACE"）
    network_mode: str | None = None         # docker 网络模式（如 "none"、"host"）
字段是否必需控制什么
image必需该实例启动的镜像——通常直接从实例里取（instance["image"]）。
workdir必需agent 的 bash 工具在哪运行、仓库在容器内的位置。
shell默认 ("bash","-lc")引导脚本被附加到的 argv 前缀；Alpine/musl 镜像用 ("/bin/sh","-lc")。
entrypoint默认 None"" 清空镜像自带的 ENTRYPOINT（有些镜像会设）；None 保留镜像默认。
platform可选强制指定架构，例如在 Apple Silicon 上用 "linux/amd64"。
cap_add默认 ()该 bench 测试所需的 Linux 权限（如 SYS_PTRACE）——漏掉是常见坑。
network_mode可选Docker 网络模式，例如 "none" 用于沙箱化、断网运行。
3
提供一个数据集加载器 必需 — 任意返回"实例 dict 可迭代对象"的函数

"整个数据集"无非就是一串 dict，每个都带有一个 instance_id。 你想怎么加载都行——HuggingFace、JSONL、某个 API。这只是一个普通函数， 不是框架的接口。

def load_instances(split="test"):
    for row in load_dataset("my/dataset", split=split):
        yield dict(row)   # 必须含 instance_id + 你的 Suite 会读取的字段
4
运行它 必需

先在进程内开发（不用 Docker、可调试），再通过替换一个参数来部署—— 套件代码本身一行都不用改。

from simple_agent_lab.evals import run_dataset, LocalDockerBackend, LocalDirStore

run_dataset(
    suite=MyBenchSuite(),
    instances=load_instances("test"),
    backend=LocalDockerBackend(),        # 本地开发可换成 LocalProcessBackend()
    store=LocalDirStore("evals/out/mybench"),
    run_root="evals/out/mybench", run_id="run-1",
    concurrency=8, provider="openai", provider_env={...},
)
5
接好输出与测试 约定

写一份 evals/out/<name>/README.md 说明输出布局，一个 runs/run_<name>.sh 便捷运行脚本，以及不依赖 Docker 的单元测试—— 用内存版 FakeBackend 驱动它，或用 LocalProcessBackend 配合确定性的 fake provider 在进程内跑真实的容器半边。

6
附带一个 oracle 自检 约定

给 suite 配一个自包含的 oracle 实例（不下载数据集），并在容器半边写一个 apply_oracle(workspace, instance)：它不调模型，而是把参考解落到 workspace。 然后用 provider="oracle" 端到端跑一遍——框架会跳过 agent 循环、应用标准答案， 你的 extract_result 应当重现出 gold 产物。这是一次确定性、无模型、无 Docker 的 校验，确认整条管线（build_task → 运行 → extract_result）接线正确、 且该实例确实可解——它与打分无关，打分是 evaluate 钩子或后续的一次 run。

# 容器半边 —— 应用 gold 解（不调模型）
def apply_oracle(workspace, instance):
    git_apply(workspace, instance["patch"])   # 参考解

# 烟测 —— 进程内、确定性；model_patch 必须等于 gold
artifacts = run_suite_instance(suite=MyBenchSuite(), instance=oracle_instance,
                               backend=LocalProcessBackend(workspace=repo),
                               store=LocalDirStore(out), run_root=out, run_id="oracle",
                               provider="oracle")

核心函数：run_dataset 的入参

run_dataset 就是整个 eval 的"控制器"——它不是进程、也不是类层级， 只是一个函数：在一个有界的 ThreadPoolExecutor 上，对每个实例调用一次无状态的 run_suite_instance。所以这里没有 Ray、没有 asyncio、没有消息队列， 主机循环本身就是控制器。它的全部参数都是关键字参数（keyword-only）：

def run_dataset(
    *,
    suite: Suite,
    instances: Iterable[Mapping[str, Any]],
    backend: ContainerBackend,
    store: ArtifactStore,
    run_root: Path,
    run_id: str,
    concurrency: int = 1,
    max_attempts: int = 1,
    on_result: Callable[[InstanceResult], None] | None = None,
    **run_kwargs: Any,   # provider / provider_env / max_turns / model_name … 透传给每个实例
) -> DatasetReport
参数类型 / 协议能力要求
suite Suite 协议（鸭子类型，@runtime_checkable） 必须提供属性 name、container_module，以及方法 launch_spec() / task_input() / eval_inputs()（eval_inputs 在别处打分时返回 None）。就是上面第 2 步那个类——无需继承任何基类，满足形状即可。
instances Iterable[Mapping[str, Any]] 实例 dict 的可迭代对象，每个 必须含 instance_id（会被 str() 化）。注意：函数内部会先 list(instances) 物化，所以惰性生成器会被一次性读完。
backend ContainerBackend 协议 决定算力在哪跑。至少实现阻塞式的 run(spec, *, store, binding)（create→wait→collect→remove）。可选实现 submit/poll 以支持主机可重入的批处理。换 backend 不改套件代码：LocalProcessBackend（进程内）↔ LocalDockerBackend（本地容器）↔ 远端。
store ArtifactStore 协议 决定字节存在哪，是主机与容器双向共享的结果总线。需实现 bind() / get() / put() / container_binding() / collect_outputs()。本地目录用 LocalDirStore（bind mount），跨机可用 HostHttpStore，未来可接对象存储——协议不变。
run_root Path 本次批处理的根目录。每个实例的产物落在 <run_root>/<run_id>/<instance_id>/，因此并发运行天然互不冲突。
run_id str 本次运行的标识，构成上面的目录层级，用来隔离不同批次。
concurrency int（默认 1） 线程池大小。1 即顺序执行、行为不变。用线程而非 async，因为 run_suite_instance 是阻塞的（Docker wait 或进程内 agent 循环）。并发安全取决于 backend 的工作区——见下方提示。
max_attempts int（默认 1） 仅在抛异常（基础设施/瞬时故障）时重试；非零退出码属于"跑完但失败"，不会重试。
on_result Callable[[InstanceResult], None] | None 可选回调，每个实例完成时在调用线程里触发一次——适合做进度条或实时聚合。
**run_kwargs 任意关键字 原样透传给每个 run_suite_instance，常见的有 provider（如 "openai" / "fake"）、provider_env、max_turns、model_name 等。

返回值是 DatasetReport：一个 results: list[InstanceResult]（按输入顺序排序， 不是完成顺序），并带有 .ok / .failed / .summary() 便捷视图。 每个 InstanceResult 里 error is None 表示"跑完未抛异常"（哪怕退出码非零）； 要看任务本身成败，读 artifacts.status_code。

最容易踩的点：并发安全取决于 backend 的工作区

Docker / 远端 backend 给每个实例独立容器，任意 concurrency 都安全。 但 LocalProcessBackend 若用固定 workspace，多个实例会共享同一目录——此时必须 concurrency=1。想在进程内也并行，就给它一个工作区工厂： LocalProcessBackend(workspace=lambda spec: base / spec.instance_id)， 每个实例各得一个目录，便可安全扇出。

两个半边之间，框架做了什么

下面这些你一行都不用写——对每个 bench 都是一样的：

没有单独的打分驱动（ADR 0020）。当 Suite 通过 eval_inputs 暂存金标时， 容器半边的 evaluate 钩子就在运行环境内打分，并把判定并入 result.json—— 复用该次 run 的容错机制。否则打分就是后续的一次 run（agent 评委），或官方 harness CLI （evaluate_predictions.py，须与官方一致）。框架产出结果，由 evaluate 钩子或后续的一次 run 裁定对错。

容器里到底跑了什么

真正在镜像里执行的，只是整个 wheel 中很窄的一条路径，不是整个仓库。容器的主进程是 引导 shell 脚本：找到 Python → pip install 安装 simple-agent-lab wheel （离线时用挂载的 wheelhouse）→ exec python -m simple_agent_lab.evals.in_container。 从这里开始，容器内执行的就是下面这几层：

会进容器执行

  • 引导脚本 + 通用 runner evals.in_container
  • agent 循环：core、agents.bash/bash_task、llm（模型调用就发生在这里）、state、trajectory、context_view
  • 你的容器半边 suites.<name>.container（及其本地 import，如 swebench 的 patch）
  • 容器侧 store 客户端：读 input/instance.json，回写 out/result.json + out/trajectory.jsonl

留在主机侧

  • run_dataset / run_suite_instance / batch.py（控制器）
  • 所有 backend（docker_local、remote_docker、local_process、fake）——它们在外面驱动容器
  • store 的服务端 HostHttpStore（容器里只有 HTTP 客户端）
  • suite 主机半边 evals/<name>/suite.py、数据集加载器、打分 evaluate_predictions.py
两个容易忽略的点

LocalProcessBackend 会把"容器半边那套代码"直接在主机进程里跑（不起容器）—— 这正是本地可断点调试得以成立的原因。而在 oracle 模式下，agent 运行时虽然仍被 import、 但不会被调用：不构建 agent、不发模型调用，只跑 apply_oracle + extract_result。

容器半边是怎么进容器并被调用的

你的容器半边（如 …/suites/swebench/container.py）从不被拷进镜像。它随 simple-agent-lab wheel 发布，在容器启动时被 pip install 进去，再通过它的 点分模块名动态导入——就是 suite 里声明的那个 container_module 字符串：

host: RunSpec(image=launch_spec.image, container_module="…suites.swebench.container", …)
  └─ docker create(image=plan.image, command=build_command(spec))          ← backend
       └─ 容器主进程 = bash -lc "<bootstrap 脚本>"
            ├─ pip install simple-agent-lab        ← container.py 随 wheel 在这一步进来
            └─ python -m simple_agent_lab.evals.in_container --container-module …swebench.container
                 └─ importlib.import_module("…swebench.container")          ← 导入你的文件
                      └─ build_task / prepare / extract_result / apply_oracle   ← 调用它

所以容器的主进程并不是你的文件本身，而是一段很小的 bootstrap 脚本：它先准备 Python、安装 wheel （离线时用挂载的 wheelhouse 配合 --find-links），再 exec 通用 in-container runner。runner 读取 --container-module，用 importlib.import_module 把你的半边导进来，然后调用它的函数。

为什么这么设计（ADR 0017）

运行时注入，不改镜像：agent 装进独立的 /opt/agent-venv，从不碰镜像 自带的环境（被测项目依赖的那套），因此上游 bench 镜像原样可用——不必为每次 agent 改动重建几百个镜像。 点分模块名而非拷文件：因为半边是从 wheel 安装的，容器里 import 到的版本永远和已安装 runtime 一致—— 这也正是为什么容器半边只能 import 标准库 + 已安装的 wheel：容器里没有别的东西。

各部分各归何处

组成部分位置为何放在这里
主机半边（Suite）evals/<name>/suite.py可能引入重型依赖（datasets、docker），不放进核心包
容器半边simple_agent_lab/evals/suites/<name>/随 wheel 发布，容器可直接 import，无需拷贝任何文件
数据集加载器由你决定只是一个函数；加载与"运行单个实例"是正交的
输出文档 + 运行脚本evals/out/<name>/、runs/跨套件统一的可复现布局约定

常见坑

坑解法
在 launch_spec 里忘了 cap_add依赖特定权限的测试会以令人困惑的错误失败——从镜像规格里取出所需权限。
在 extract_result 上漏掉 *, contextprepare() 的准备结果到不了提取阶段 → 拿到错误的产物。
容器半边里引入重型依赖它在镜像内 import 会失败——只用标准库 + 已安装的 wheel。
在 runner 里写 if dataset == …把差异表达成 LaunchSpec 数据，而不是分支。
