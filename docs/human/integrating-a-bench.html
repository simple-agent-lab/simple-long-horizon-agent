Integrating a benchmark

The standard way to add a new Docker-based eval suite to this framework.

The framework already owns the hard, generic parts: the container lifecycle, the Python bootstrap, the run-directory layout, moving bytes in and out, concurrency, and host-reentrant batches. You write two small halves and register them. You do not modify the benchmark image, and you do not copy the agent into it — it is installed when the container starts.

The shape of an integration

A benchmark is fundamentally two programs that meet at a shared artifact store: a host half that decides how to launch each instance and how to read the result, and a container half that runs inside the image and does the actual task. You implement both; everything between them is the framework.

Host half — a Suite

  • name & container_module — identity + dotted path to the container half
  • container_plan(instance) — image, workdir, shell, entrypoint, cap_add as data (no if-branching)
  • sanitize_instance(instance) — drop the gold/answer fields before the agent sees it
  • prediction_record(instance, …, result) — shape the scorer-facing row
lives under evals/<name>/suite.py · may use heavy deps (datasets, docker)

Container half — two functions

  • build_task(instance, *, workdir) — turn the instance into the agent's task
  • extract_result(workspace, instance, *, context) — read the run's product (e.g. a git diff)
  • optional prepare(...) — pre-run setup, fed back as context
  • optional agent_spec() / build_agent(...) — choose/customize the agent
ships in the wheel at simple_agent_lab/evals/suites/<name>/ · stdlib + installed runtime only

The five steps

1
Write the container half required — src/simple_agent_lab/evals/suites/<name>/container.py

The code that runs inside the image. It imports only the standard library and the installed simple_agent_lab runtime, because the benchmark image has nothing else.

# build_task: instance dict -> the model-visible task
def build_task(instance, *, workdir):
    return f"Fix this bug in {workdir}:\n{instance['problem_statement']}"

# extract_result: read the agent's effect on the workspace (not its chat)
# Declare *, context even if unused — that's how prepare()'s output reaches you.
def extract_result(workspace, instance, *, context=None):
    return {"model_patch": git_diff(workspace)}
2
Write the host half required — evals/<name>/suite.py

A class satisfying the Suite protocol. The per-instance differences (which image, where the repo lives, what capabilities the tests need) are expressed as data in container_plan — never as branches in the runner.

class MyBenchSuite:
    name = "mybench"
    container_module = "simple_agent_lab.evals.suites.mybench.container"

    def container_plan(self, instance):
        return ContainerPlan(image=instance["image"], workdir="/repo",
                             cap_add=("SYS_PTRACE",))   # caps the tests need
    def sanitize_instance(self, instance):
        return {k: v for k, v in instance.items() if k != "gold_patch"}
    def prediction_record(self, instance, *, model_name, result):
        return {"instance_id": instance["instance_id"], "model_patch": result["model_patch"]}
3
Provide a dataset loader required — any function returning an iterable of instance dicts

"The whole dataset" is just a stream of dicts, each with an instance_id. Load them however you like — HuggingFace, JSONL, an API. This is a plain function, not a framework interface.

def load_instances(split="test"):
    for row in load_dataset("my/dataset", split=split):
        yield dict(row)   # must contain instance_id + whatever your Suite reads
4
Run it required

Develop in-process (no Docker, debuggable), then deploy by swapping one argument — the suite code does not change.

from simple_agent_lab.evals import run_dataset, LocalDockerBackend, LocalDirStore

run_dataset(
    suite=MyBenchSuite(),
    instances=load_instances("test"),
    backend=LocalDockerBackend(),        # or LocalProcessBackend() for local dev
    store=LocalDirStore("evals/out/mybench"),
    run_root="evals/out/mybench", run_id="run-1",
    concurrency=8, provider="openai", provider_env={...},
)
5
Wire up outputs & tests convention

An evals/out/<name>/README.md documenting the output layout, a runs/run_<name>.sh convenience runner, and unit tests that exercise the suite with no Docker — drive it with the in-memory FakeBackend, or run the real container half in-process with LocalProcessBackend and the deterministic fake provider.

What the framework does between your two halves

You never write any of this — it is the same for every benchmark:

HOST                              STORE                 CONTAINER (your image)
container_plan() ── launch shape
sanitize_instance() ─ write ───▶ input/instance.json
start container ───────────────────────────────────▶  bootstrap: pip install runner
  (wait)                                                build_task()  ← your code
                                                        run the agent loop
                                 trajectory.jsonl ◀──     (model calls + bash edits)
                                 out/result.json  ◀──   extract_result()  ← your code
read result ◀── prediction_record() ─▶ out/prediction.jsonl

Scoring is a separate, official step: a clean container applies each prediction.jsonl patch and runs the benchmark's tests. The framework produces patches; it never decides correctness.

Common pitfalls

PitfallFix
Forgetting cap_add in container_planCapability-dependent tests fail with confusing errors — pull caps from the image's spec.
Omitting *, context on extract_resultprepare()'s setup never reaches extraction → wrong product.
Heavy imports in the container halfIt fails to import inside the image — keep it stdlib + the installed wheel.
Putting if dataset == … in the runnerExpress the difference as ContainerPlan data instead.
