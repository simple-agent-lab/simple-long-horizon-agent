Integrating a benchmark

The standard way to add a new Docker-based eval suite to this framework.

The framework already owns the hard, generic parts: the container lifecycle, the Python bootstrap, the run-directory layout, moving bytes in and out, concurrency, and host-reentrant batches. You write two small halves and register them. You do not modify the benchmark image, and you do not copy the agent into it — it is installed when the container starts.

The shape of an integration

A benchmark is fundamentally two programs that meet at a shared artifact store: a host half that decides how to launch each instance and how to read the result, and a container half that runs inside the image and does the actual task. You implement both; everything between them is the framework.

Host half — a Suite

  • name & container_module — identity + dotted path to the container half
  • launch_spec(instance) — image, workdir, shell, entrypoint, cap_add as data (no if-branching)
  • task_input(instance) — drop the gold/answer fields before the agent sees it
  • eval_inputs(instance) — gold scoring inputs staged for the container half's evaluate hook (in-environment scoring), or None to score elsewhere. Staging gold is the toggle that turns the hook on (ADR 0020) — there is no separate scorer() method.
lives under evals/<name>/suite.py · may use heavy deps (datasets, docker)

Container half — two functions

  • build_task(instance, *, workdir) — turn the instance into the agent's task prompt (a string, or content blocks for multimodal — text + images). It only builds the prompt; the agent loop is the framework's.
  • extract_result(workspace, instance, *, context) — read the run's product (e.g. a git diff)
  • optional prepare(...) — pre-run setup, fed back as context
  • optional apply_oracle(workspace, instance) — apply the reference solution for the model-free self-check
  • optional agent_spec() / build_agent(...) — choose/customize the agent
ships in the wheel at simple_agent_lab/evals/suites/<name>/ · stdlib + installed runtime only

The five steps

1
Write the container half required — src/simple_agent_lab/evals/suites/<name>/container.py

The code that runs inside the image. It imports only the standard library and the installed simple_agent_lab runtime, because the benchmark image has nothing else.

# build_task: instance dict -> the model-visible task prompt.
# Return a str, or a list of content blocks for multimodal (text + images).
def build_task(instance, *, workdir):
    return f"Fix this bug in {workdir}:\n{instance['problem_statement']}"

# extract_result: read the agent's effect on the workspace (not its chat)
# Declare *, context even if unused — that's how prepare()'s output reaches you.
def extract_result(workspace, instance, *, context=None):
    return {"model_patch": git_diff(workspace)}
2
Write the host half required — evals/<name>/suite.py

A class satisfying the Suite protocol. The per-instance differences (which image, where the repo lives, what capabilities the tests need) are expressed as data in launch_spec — never as branches in the runner.

class MyBenchSuite:
    name = "mybench"
    container_module = "simple_agent_lab.evals.suites.mybench.container"

    def launch_spec(self, instance):
        return LaunchSpec(image=instance["image"], workdir="/repo",
                             cap_add=("SYS_PTRACE",))   # caps the tests need
    def task_input(self, instance):
        return {k: v for k, v in instance.items() if k != "gold_patch"}
    # Stage gold for the container half's `evaluate` hook (in-environment
    # scoring, ADR 0020). Return None to score elsewhere (a follow-up run or
    # the official harness CLI). There is no separate scorer() method.
    def eval_inputs(self, instance):
        return {"expected": instance["gold_patch"]}   # or None to score elsewhere

LaunchSpec is a frozen dataclass — pure launch data, no behavior. The per-instance differences live here, never as if-branches:

class LaunchSpec:
    image: str                              # the Docker image for this instance
    workdir: str                            # cwd inside the container (e.g. /testbed, /app)
    shell: tuple[str, ...] = ("bash", "-lc")  # argv prefix the bootstrap is run under
    entrypoint: str | None = None           # ""=clear image ENTRYPOINT; None=keep image default
    platform: str | None = None             # e.g. "linux/amd64"
    cap_add: tuple[str, ...] = ()           # Linux caps the tests need (e.g. "SYS_PTRACE")
    network_mode: str | None = None         # docker network mode (e.g. "none", "host")
FieldRequired?What it controls
imagerequiredThe image launched for this instance — usually read off the instance (instance["image"]).
workdirrequiredWhere the agent's bash tool runs and where the repo lives inside the container.
shelldefault ("bash","-lc")The argv prefix the bootstrap script is handed to; Alpine/musl images use ("/bin/sh","-lc").
entrypointdefault None"" clears an image's ENTRYPOINT (some images set one); None keeps the image default.
platformoptionalForce an architecture, e.g. "linux/amd64" on Apple Silicon.
cap_adddefault ()Linux capabilities the benchmark's tests require (e.g. SYS_PTRACE) — forgetting these is a common pitfall.
network_modeoptionalDocker network mode, e.g. "none" for a sandboxed, offline run.
3
Provide a dataset loader required — any function returning an iterable of instance dicts

"The whole dataset" is just a stream of dicts, each with an instance_id. Load them however you like — HuggingFace, JSONL, an API. This is a plain function, not a framework interface.

def load_instances(split="test"):
    for row in load_dataset("my/dataset", split=split):
        yield dict(row)   # must contain instance_id + whatever your Suite reads
4
Run it required

Develop in-process (no Docker, debuggable), then deploy by swapping one argument — the suite code does not change.

from simple_agent_lab.evals import run_dataset, LocalDockerBackend, LocalDirStore

run_dataset(
    suite=MyBenchSuite(),
    instances=load_instances("test"),
    backend=LocalDockerBackend(),        # or LocalProcessBackend() for local dev
    store=LocalDirStore("evals/out/mybench"),
    run_root="evals/out/mybench", run_id="run-1",
    concurrency=8, provider="openai", provider_env={...},
)
5
Wire up outputs & tests convention

An evals/out/<name>/README.md documenting the output layout, a runs/run_<name>.sh convenience runner, and unit tests that exercise the suite with no Docker — drive it with the in-memory FakeBackend, or run the real container half in-process with LocalProcessBackend and the deterministic fake provider.

6
Ship an oracle self-check convention

Add a tiny self-contained oracle instance (no dataset download) plus an apply_oracle(workspace, instance) in your container half that lands the reference solution instead of calling a model. Then run the suite end-to-end with provider="oracle": the framework skips the agent loop, applies the gold solution, and your extract_result must reproduce the gold product. This is a deterministic, model-free, Docker-free check that the whole pipeline (build_task → run → extract_result) is wired correctly and the instance is actually solvable — distinct from scoring, which is the evaluate hook or a follow-up run.

# container half — apply the gold solution (no model)
def apply_oracle(workspace, instance):
    git_apply(workspace, instance["patch"])   # the reference solution

# smoke test — in-process, deterministic; model_patch must equal the gold
artifacts = run_suite_instance(suite=MyBenchSuite(), instance=oracle_instance,
                               backend=LocalProcessBackend(workspace=repo),
                               store=LocalDirStore(out), run_root=out, run_id="oracle",
                               provider="oracle")

What the framework does between your two halves

You never write any of this — it is the same for every benchmark:

HOST                              STORE                 CONTAINER (your image)
launch_spec() ── launch shape
task_input() ─ write ───▶ input/instance.json
start container ───────────────────────────────────▶  bootstrap: pip install runner
  (wait)                                                build_task()  ← your code
                                                        run the agent loop
                                 trajectory.jsonl ◀──     (model calls + bash edits)
                                 out/result.json  ◀──   extract_result()  ← your code
                                 out/result.json  ◀──   evaluate()  ← optional, merges verdict
read result.json ◀──────────────  (verdict included)

There is no separate scoring driver (ADR 0020). When a suite stages gold via eval_inputs, the container half's evaluate hook scores in the run environment and merges its verdict into result.json — reusing the run's fault tolerance. Otherwise scoring is a follow-up run (an agent judge) or the official harness CLI (evaluate_predictions.py, which must match official parity). The framework produces results; the evaluate hook or a follow-up run decides correctness.

What actually runs inside the container

Only a narrow slice of the wheel executes in the image — not the whole repo. The container's main process is the bootstrap shell script, which finds a Python, pip installs the simple-agent-lab wheel (from a mounted wheelhouse when offline), then execs python -m simple_agent_lab.evals.in_container. From there the in-container code is:

bootstrap.sh  →  python -m simple_agent_lab.evals.in_container   (the generic runner)
                   ├─ agent runtime ....... core · agents.bash/​bash_task · llm · state · trajectory · context_view
                   ├─ your container half .. simple_agent_lab.evals.suites.<name>.container  (build_task / prepare / extract_result / apply_oracle)
                   └─ store client ......... container_store_from_env() → LocalDirStore (bind mount) | HttpArtifactClient (http)

Runs in the container

  • the bootstrap script + the generic runner evals.in_container
  • the agent loop: core, agents.bash/bash_task, llm (the model call happens here), state, trajectory, context_view
  • your container half suites.<name>.container (+ its local imports, e.g. swebench's patch)
  • the container-side store client (reads input/instance.json, writes out/result.json + out/trajectory.jsonl)

Stays on the host

  • run_dataset / run_suite_instance / batch.py (the controller)
  • every backend (docker_local, remote_docker, local_process, fake) — they drive the container from outside
  • the store server HostHttpStore (the container only has the HTTP client)
  • the suite host half evals/<name>/suite.py, the dataset loader, and scoring (evaluate_predictions.py)
Two subtleties

LocalProcessBackend runs that same container-half code in the host process (no container) — that is why local, debugger-friendly development works. And in oracle mode the agent runtime is still imported but never invoked: no agent is built and no model is called; only apply_oracle + extract_result run.

How the container half gets in and runs

Your container half (e.g. …/suites/swebench/container.py) is never copied into the image. It ships in the simple-agent-lab wheel, is pip installed at container start, and is imported by its dotted module path — the same string the suite declares as container_module:

host: RunSpec(image=launch_spec.image, container_module="…suites.swebench.container", …)
  └─ docker create(image=plan.image, command=build_command(spec))          ← the backend
       └─ container main process = bash -lc "<bootstrap script>"
            ├─ pip install simple-agent-lab        ← container.py arrives here, inside the wheel
            └─ python -m simple_agent_lab.evals.in_container --container-module …swebench.container
                 └─ importlib.import_module("…swebench.container")          ← imports your file
                      └─ build_task / prepare / extract_result / apply_oracle   ← calls it

So the container's main process is not your file directly — it is a tiny bootstrap script that prepares Python, installs the wheel (offline via a mounted wheelhouse with --find-links), then execs the generic in-container runner. The runner reads --container-module and importlib.import_modules your half, then calls its functions.

Why this way (ADR 0017)

Runtime injection, not modified images: the agent installs into an isolated /opt/agent-venv and never touches the image's own environment (the one the benchmark under test depends on), so upstream bench images are used unchanged — no rebuilding hundreds of images per agent change. Dotted module, not file copy: because the half is installed from the wheel, the version imported in the container always matches the installed runtime — which is exactly why the container half may import only the standard library and the installed wheel: nothing else exists in there.
