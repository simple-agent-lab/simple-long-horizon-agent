Running offline with LocalDockerBackend

Run container evals with no PyPI access — feed the runtime in as read-only bind mounts.

The agent runtime is not baked into the benchmark image; it is installed when the container starts. Normally that install reaches PyPI. When you have no published package, an air-gapped daemon, or want reproducible pins, you instead hand the container a prebuilt wheelhouse (and, for old images, a uv binary). LocalDockerBackend bind-mounts both read-only, and the bootstrap installs with --no-index.

The three pieces

Wheelhouse — deps offline

  • A directory of wheels: the project wheel plus every runtime dependency.
  • Built from uv.lock, so versions are exact, reproducible pins (not re-resolved >= ranges).
  • Bind-mounted read-only; the bootstrap runs pip install --no-index --find-links against it.
targets the container's cp311 + x86_64 ABI

uv binary — a 3.11 venv

  • Optional. Needed only when the image's own Python predates 3.11 (the wheels' target).
  • A Linux uv, mounted at /tmp/uv (the bootstrap probes there first).
  • It builds /opt/agent-venv on Python 3.11 — using a 3.11 already in the image, or fetching one.
must match the container's OS/arch, not the host's
  host                                   container (benchmark image, unchanged)
  ────                                   ─────────────────────────────────────
  wheelhouse/  ──bind ro──▶  /agent/wheelhouse ─┐
  uv (linux)   ──bind ro──▶  /tmp/uv ───────────┤
  run dir/     ──bind rw──▶  /agent/run          │  bootstrap:
                                                 ├─▶ uv venv --python 3.11 /opt/agent-venv
                                                 ├─▶ uv pip install --no-index
                                                 │     --find-links /agent/wheelhouse simple-agent-lab
                                                 └─▶ python -m simple_agent_lab.evals.in_container …
  result.json ◀──────────────────────────────────  (written through the bound store)

Step by step

1
Build the wheelhouse required

The SWE-bench reference helper builds it straight from uv.lock: it uv builds the project wheel, uv exports the locked runtime closure, then pip downloads those exact versions for the container ABI.

from pathlib import Path
from evals.swebench.harness import prepare_wheelhouse

prepare_wheelhouse(Path("evals/out/wheelhouse"))   # project wheel + locked deps (cp311, x86_64)

For a non-SWE-bench project the same three commands are the whole recipe: uv build --wheel --out-dir DIR · uv export --frozen --no-dev --no-emit-project --format requirements.txt -o DIR/req.txt · pip download --only-binary=:all: --python-version 311 --abi cp311 --platform manylinux2014_x86_64 -r DIR/req.txt -d DIR.

2
Get a Linux uv only for pre-3.11 images

If the benchmark image already has Python 3.11 (or any uv on its PATH), skip this. Otherwise fetch a uv for the container's platform — not your Mac's.

# x86_64 Linux uv (matches the cp311/x86_64 wheelhouse)
curl -LsSf https://github.com/astral-sh/uv/releases/download/0.11.17/uv-x86_64-unknown-linux-gnu.tar.gz \
  | tar -xz -C evals/out/uv-linux --strip-components=1
3
Point LocalDockerBackend at them required

The backend bind-mounts the wheelhouse at the run's wheelhouse_mount and the uv binary at /tmp/uv — both read-only. The run carries wheelhouse_mount (the in-container --find-links path) so the bootstrap installs offline.

from simple_agent_lab.evals import run_dataset, LocalDockerBackend, LocalDirStore

run_dataset(
    suite=MyBenchSuite(),
    instances=load_instances("test"),
    backend=LocalDockerBackend(
        wheelhouse="evals/out/wheelhouse",        # bind ro → wheelhouse_mount
        uv_binary="evals/out/uv-linux/uv",        # bind ro → /tmp/uv (omit if image has 3.11)
        pull="never",                            # the image is already local
    ),
    store=LocalDirStore("evals/out/mybench"),
    run_root="evals/out/mybench", run_id="run-1",
    wheelhouse_mount="/agent/wheelhouse",         # the --no-index --find-links dir
    provider="openai", provider_env={...},
)
4
Verify without a model: oracle mode recommended

Before spending a model run, prove the whole offline pipeline — mounts, bootstrap, install, container half — with provider="oracle". It skips the agent loop, applies the suite's reference solution (apply_oracle), and the result should reproduce the gold patch. Deterministic, no API key, no network beyond the image.

How it works inside

Two seams do the work. The backend augments the store's binding with read-only mounts; the bootstrap consumes them.

WhereWhat happens
with_local_mounts(...)
docker_local.py		Adds {wheelhouse → wheelhouse_mount, "ro"} and {uv → /tmp/uv, "ro"} to the ContainerBinding, beside the store's own run-dir mount. A wheelhouse with no wheelhouse_mount is a loud error.
bootstrap_script(...)
bootstrap.py		Probes /tmp/uv first, then uv on PATH, then a system python3 venv. With a wheelhouse_mount set, the install line is uv pip install --python $AGENT_PYTHON --no-index --find-links <mount> simple-agent-lab.
the container halfImported by dotted path from the now-installed wheel — so the version in the container always matches what the wheelhouse shipped.
Shared filesystem, like the store

LocalDockerBackend delivers everything by bind mount — the same assumption LocalDirStore already makes (the daemon shares this filesystem). If your daemon cannot see the host path (a worker behind a network, a VM that does not mount the project dir), bind mounts silently resolve to empty. Use a host-pull backend (RemoteDockerBackend + put_archive / HostHttpStore) instead, which copies bytes over the daemon connection.

Pitfalls

PitfallFix
Wheelhouse ABI mismatchThe wheels are cp311 + x86_64. On Apple Silicon set LaunchSpec.platform="linux/amd64" and run x86_64 images (emulated); a 3.11 venv is still required.
Wrong uv buildThe mounted uv must be the container's OS/arch (Linux x86_64), not the host's macOS/arm64 binary — the latter fails its --version probe and the bootstrap silently falls back.
Empty /agent/wheelhouseAlmost always a non-shared daemon (remote / VM not mounting the path). Confirm with docker run -v "$PWD/wheelhouse":/wh … ls /wh; if empty, switch to the host-pull backend.
docker-py can't find the daemonThe CLI uses a context; docker-py reads DOCKER_HOST. For colima: export DOCKER_HOST="unix://$HOME/.colima/default/docker.sock".
Re-installing when the image already has the wheelPass install=False so the bootstrap skips the install step entirely.
Stale deps after a bumpThe wheelhouse is built once; after editing pyproject.toml / uv.lock, rebuild it (delete + re-run prepare_wheelhouse) so the new pins land.
