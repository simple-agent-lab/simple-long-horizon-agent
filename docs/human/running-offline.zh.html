用 LocalDockerBackend 离线运行

在无法访问 PyPI 的环境里跑容器化 eval —— 把运行时以只读 bind mount 喂进容器。

agent 运行时不会烤进 bench 镜像，而是在容器启动时安装。这一步默认走 PyPI。 当你没有发布 pip 包、daemon 处于隔离网络、或想要可复现的精确版本时，就改为把一个预构建的 wheelhouse（以及给老镜像准备的 uv 二进制）交给容器。LocalDockerBackend 会把两者只读 bind-mount 进去，bootstrap 用 --no-index 离线安装。

三个部件

Wheelhouse —— 离线依赖

  • 一个装满 wheel 的目录：项目 wheel + 全部运行时依赖。
  • 从 uv.lock 构建，所以版本是精确、可复现的 pin（不是每次重新解析的 >= 范围）。
  • 只读挂载；bootstrap 对它执行 pip install --no-index --find-links。
针对容器的 cp311 + x86_64 ABI

uv 二进制 —— 造 3.11 venv

  • 可选。仅当镜像自带 Python 早于 3.11（wheel 的目标版本）时才需要。
  • 一个 Linux 版 uv，挂到 /tmp/uv（bootstrap 优先探测这里）。
  • 它用 Python 3.11 造出 /opt/agent-venv——复用镜像里已有的 3.11，或现拉一个。
必须匹配容器的 OS/架构，不是宿主的
  宿主                                   容器（bench 镜像，保持不变）
  ────                                   ────────────────────────────
  wheelhouse/  ──只读挂载──▶  /agent/wheelhouse ─┐
  uv (linux)   ──只读挂载──▶  /tmp/uv ───────────┤
  run 目录/    ──读写挂载──▶  /agent/run          │  bootstrap：
                                                 ├─▶ uv venv --python 3.11 /opt/agent-venv
                                                 ├─▶ uv pip install --no-index
                                                 │     --find-links /agent/wheelhouse simple-agent-lab
                                                 └─▶ python -m simple_agent_lab.evals.in_container …
  result.json ◀──────────────────────────────────  （经绑定的 store 写回）

分步操作

1
构建 wheelhouse 必需

SWE-bench 的参考辅助函数直接从 uv.lock 构建：uv build 出项目 wheel， uv export 导出锁定的运行时闭包，再 pip download 按容器 ABI 抓那些精确版本。

from pathlib import Path
from evals.swebench.harness import prepare_wheelhouse

prepare_wheelhouse(Path("evals/out/wheelhouse"))   # 项目 wheel + 锁定依赖（cp311, x86_64）

非 SWE-bench 项目，等价配方就是这三条命令： uv build --wheel --out-dir DIR · uv export --frozen --no-dev --no-emit-project --format requirements.txt -o DIR/req.txt · pip download --only-binary=:all: --python-version 311 --abi cp311 --platform manylinux2014_x86_64 -r DIR/req.txt -d DIR。

2
准备一个 Linux uv 仅老镜像需要

如果 bench 镜像已自带 Python 3.11（或 PATH 上有任意 uv），跳过这步。 否则抓一个容器平台的 uv——不是你 Mac 的。

# x86_64 Linux 版 uv（匹配 cp311/x86_64 的 wheelhouse）
curl -LsSf https://github.com/astral-sh/uv/releases/download/0.11.17/uv-x86_64-unknown-linux-gnu.tar.gz \
  | tar -xz -C evals/out/uv-linux --strip-components=1
3
让 LocalDockerBackend 指向它们 必需

backend 会把 wheelhouse 挂到 run 的 wheelhouse_mount、把 uv 挂到 /tmp/uv——都是只读。run 携带 wheelhouse_mount（容器内 --find-links 的路径），bootstrap 据此离线安装。

from simple_agent_lab.evals import run_dataset, LocalDockerBackend, LocalDirStore

run_dataset(
    suite=MyBenchSuite(),
    instances=load_instances("test"),
    backend=LocalDockerBackend(
        wheelhouse="evals/out/wheelhouse",        # 只读挂载 → wheelhouse_mount
        uv_binary="evals/out/uv-linux/uv",        # 只读挂载 → /tmp/uv（镜像有 3.11 则省略）
        pull="never",                            # 镜像已在本地
    ),
    store=LocalDirStore("evals/out/mybench"),
    run_root="evals/out/mybench", run_id="run-1",
    wheelhouse_mount="/agent/wheelhouse",         # 即 --no-index --find-links 的目录
    provider="openai", provider_env={...},
)
4
不用模型先验证：oracle 模式 推荐

在花一次模型运行之前，用 provider="oracle" 把整条离线流水线——挂载、bootstrap、安装、 容器半边——先验一遍。它跳过 agent 循环，应用 suite 的参考解（apply_oracle），结果应当复现 gold patch。确定性、无需 API key、除镜像外不依赖网络。

内部是怎么跑的

两个接缝完成工作：backend 给 store 的 binding 增补只读挂载，bootstrap 消费它们。

位置做了什么
with_local_mounts(...)
docker_local.py		在 ContainerBinding 里，于 store 自己的 run 目录挂载之外，加上 {wheelhouse → wheelhouse_mount, "ro"} 和 {uv → /tmp/uv, "ro"}。设了 wheelhouse 却没给 wheelhouse_mount 会清晰报错。
bootstrap_script(...)
bootstrap.py		先探 /tmp/uv，再探 PATH 上的 uv，最后退化到系统 python3 venv。设了 wheelhouse_mount 时，安装命令为 uv pip install --python $AGENT_PYTHON --no-index --find-links <mount> simple-agent-lab。
容器半边从刚装好的 wheel 按点分模块路径导入——所以容器里的版本永远与 wheelhouse 发的一致。
和 store 一样，假设共享文件系统

LocalDockerBackend 全靠 bind mount 投递——这正是 LocalDirStore 已经做的假设（daemon 与本机共享文件系统）。如果你的 daemon 看不到宿主路径（worker 在另一台机器、或 VM 没挂载项目目录），bind mount 会静默解析成空目录。这种情况改用 host-pull 的 backend （RemoteDockerBackend + put_archive / HostHttpStore），通过 daemon 连接把字节拷过去。

坑

坑解法
Wheelhouse ABI 不匹配wheel 是 cp311 + x86_64。Apple Silicon 上要设 LaunchSpec.platform="linux/amd64" 并跑 x86_64 镜像（模拟执行）；仍然需要一个 3.11 venv。
uv 构建版本不对挂进去的 uv 必须是容器的 OS/架构（Linux x86_64），不是宿主的 macOS/arm64 那个——后者过不了 --version 探测，bootstrap 会静默退化。
/agent/wheelhouse 是空的几乎都是 daemon 不共享文件系统（远程 / VM 没挂该路径）。用 docker run -v "$PWD/wheelhouse":/wh … ls /wh 确认；为空就换成 host-pull backend。
docker-py 找不到 daemonCLI 走 context，docker-py 读 DOCKER_HOST。colima：export DOCKER_HOST="unix://$HOME/.colima/default/docker.sock"。
镜像已含 wheel 还重复安装传 install=False，让 bootstrap 整个跳过安装步骤。
升级依赖后还是旧版wheelhouse 只构建一次；改了 pyproject.toml / uv.lock 后要重建（删除目录再跑一次 prepare_wheelhouse），新 pin 才会进去。
