① 多轮 Rollout 总控 — multi_turn_loop() → vanilla_multi_turn_loop()
这一步在做什么？
这是整个 Rollout 阶段的外层驱动函数，位于 agentic_trainer.fit() 内部，一行代码触发：

gen_batch_output = self.traj_collector.multi_turn_loop(gen_batch, inferencer, envs, is_train=True)

它内部调用 vanilla_multi_turn_loop()，后者用一个 for 循环（最多 max_steps=10 次）驱动节点 2~6 反复执行：每轮先重置 env 拿 obs，再让 LLM 生成、格式校验、env 执行、算奖励，直到所有 env 的 done=True 或达到 max_steps。 循环结束后把所有轨迹打包成一个 DataProto 返回给 trainer。
调用栈两层函数嵌套
agentic_trainer.fit()
  └─ traj_collector.multi_turn_loop(gen_batch, inferencer, envs, is_train=True)
       │
       ├─ gen_batch.repeat(n=4, interleave=True)   ← 把 2 条 prompt 扩成 8 条（每题 4 份）
       │
       └─ vanilla_multi_turn_loop(gen_batch, inferencer, envs)
            │
            ├─ envs.reset()                         ← 节点 2
            ├─ for _step in range(max_steps=10):
            │    ├─ inferencer.generate_sequences() ← 节点 3
            │    ├─ bfcl_projection()               ← 节点 4
            │    ├─ envs.step()                     ← 节点 5 + 6
            │    └─ if all done: break
            └─ envs.success_evaluator()             ← 节点 10
OUTPUT — 返回给 agentic_trainergen_batch_output: DataProto

🔑
为什么叫 vanilla（朴素）multi_turn_loop？

相对于 dynamic_multi_turn_loop（用于 DAPO/GiGPO，会过滤低质量 group 再重采样）。当前配置 filter_groups.enable=False，所以直接走 vanilla 版本——8 个 env 的轨迹不过滤，全部送去训练。

💡
gen_batch_output 的行数 N 是变长的

8 个 env，每个 env 最多跑 10 步，但 done 后就停。所以 N 的范围是 8（所有 env 第1步就 done）到 80（全部跑满）。trainer 在拿到这个 DataProto 后会 pad_dataproto_to_divisor(dp_size=2) 补齐。

⚠️
skip_special_tokens=False 是关键（v17 修复）

L393 解码时用 skip_special_tokens=False，保留 Qwen 的 <tool_call>/</tool_call> added tokens（token id 151657/151658）。早期用 True 会剥掉这些标签，BfclEnv 的 XMLParser 解析失败，episode reward 全为 0。

① 环境重置 — BfclVectorizedEnv.reset()
这一步在做什么？

🔑
为什么要 np.repeat？

GRPO 要求同一道题的 n=4 个 rollout 放在同一组才能计算组内 advantage。np.repeat([A,B], 4) 保证 8 个 env 中，前4个跑题A、后4个跑题B，训练时按 group_n=4 分组算 (r - μ) / σ。

⚠️
task_key 必须是字符串（Round 1 踩坑）

BfclEnv 内部 dataset 的 key 是 "multi_turn_base_142" 这种字符串，直接传 int 142 会 KeyError。这是早期调试发现的 19 个坑之一。

💡
为什么 temperature=1.5 这么高？

GRPO 需要同组 4 个 rollout 有不同的输出，才能计算组内 std。temperature 太低（如 0.4）会让 4 个输出几乎一样，std→0，advantage→0，训练停滞。1.5 保证足够多样性，代价是偶尔输出格式混乱。

🔧
skip_special_tokens=False（v17 修复）

早期用 skip_special_tokens=True 解码，会剥掉 Qwen2.5 的 added tokens，导致 <tool_call> 标签丢失，BfclEnv 解析失败。改为 False 后模型才开始正常输出 XML 格式。

🔑
func_score × 40 为什么是 40？

v23 用的是 ×20（max=10），但当时 turn_advance +1.0×5=5 > terminal，模型学会了每步刷 "Task Completed"。v25 把 terminal 调到 ×40（max=20），让 terminal(20) >> turn_advance(0.5)，消除快钱漏洞。

📊
func_score 是 BFCL 的 partial credit

BFCL 原生支持部分得分：每个 turn 的工具调用里，答对 k/n 个参数得 k/n 分（不是全对才给分）。func_score 范围 0~0.5，×2 得 0~1 的 func_acc。这比 all-or-nothing 提供更丰富的学习信号。

⑤ per-step 奖励计算 — BfclEnvironmentManager.step()
这一步在做什么？
在 BfclEnv 返回的 terminal reward 基础上，再叠加 per-step shaping reward： 根据 obs_type 信号判断这一步的结果，给出 +0.1 / -0.1 / -0.2 的微小调整。

设计目标：让每个 step 有不同的奖励值，让 GRPO 组内有方差，训练不坍塌。 当前问题：+0.1 仍被模型在 step 15 后饱和（每步刷 Task Completed）。
奖励规则表（v26）per-step shaping
obs_type == "user"   (模型发了Task Completed，turn推进)  → step_r = +0.1
obs_type == "tool"   + 执行出错                          → step_r = -0.1
没有 <tool_call> 标签  (退化输出)                          → step_r = -0.2
其他（工具执行成功）                                         → step_r = 0.0

terminal reward (仅 done=True 时)：
  func_score × 40  → 0 ~ 20.0   ← 主要学习信号

一个 episode 的最大总奖励：
  5轮 × turn_advance(0.1) + terminal(20) = 20.5
核心代码 verl/recipe/sdpo/bfcl/bfcl_env_manager.py : step() 奖励部分

🐛
v26 仍然被饱和（step 15-16 坍塌）

v26 step 15-16 出现 score=[0.1, 0.1]，4 个 rollout 全都在每步刷 "Task Completed"，拿 +0.1。 turn_advance 只有 0.1 理论上不会超过 terminal，但 cold-start 阶段 func_score≈0， 模型比较的是 0.5（刷满5次）vs ~0（terminal），所以还是选快钱。

💡
根本矛盾：任何正值 per-step reward 都会被饱和

常数正值 → 模型学会"每步触发" → 组内4个rollout全部相同 → std=0 → GRPO advantage=0 → 零梯度。 需要一种有自然方差且不可饱和的 per-step 信号（如 entropy bonus，或 mid-episode func_score diff）。

⑥ 奖励注入 tensor — AgenticBFCLTrainer.fit()
这一步在做什么？
把每个 step 的标量 reward（一个浮点数）放进 shape=[8, 512] 的 tensor， 放置位置是 response 的最后一个有效 token，其余位置填 0。

这是 v24 的根因修复：之前用的是 episode_total（整个 episode 的总分）， 赋给 episode 内所有 step，导致同一 episode 的每步奖励相同，组内 std=0。 改用 per-step reward 后，每步奖励不同，GRPO 才有梯度信号。
v23 之前的错误方式episode_rewards
❌ 错误：episode_total 赋给 episode 内所有 step
episode rollout：step1, step2, step3, step4, step5
  step1.reward = 3.2  (episode总分)
  step2.reward = 3.2  ← 全部相同
  step3.reward = 3.2  ← 全部相同
GRPO组内：所有 step score = 3.2 → std = 0 → advantage = 0 → 零梯度
v24 修复后的正确方式per-step rewards
✅ 正确：每个 step 有自己的 reward
  step1.reward = 0.1   (turn_advanced)
  step2.reward = -0.1  (tool error)
  step3.reward = 0.0   (valid tool call)
  step4.reward = 0.1   (turn_advanced)
  step5.reward = 8.0   (terminal: func_score=0.2 × 40)
GRPO组内：不同step有不同score → std > 0 → advantage ≠ 0 → 有效梯度

为什么 reward 放在"最后一个 token"？

verl GRPO 的实现：scores = token_level_rewards.sum(dim=-1)，把 shape=[bsz,512] 的 token reward 按行求和，得到 [bsz] 的标量分数，再按 group 归一化。 把 reward 集中放最后一个 token，等效于 sequence-level reward，数学上等价，实现上最简单。

⑦ GRPO Advantage 计算 — compute_advantage()
这一步在做什么？
把 8 个 step 的 token_level_scores（每步一个标量）按 group_n=4 分组， 在组内做归一化：adv = (score_i - mean_group) / std_group。

直觉：同一道题的 4 个 rollout，谁做得比平均好就给正 adv，谁比平均差就给负 adv。 不需要绝对分数，只看相对排名。
一个 group (n=4) 的计算示例关键数学
同一道题的4条轨迹分数：
  rollout_A: score = 8.1   (func_score=0.2, turn×1)
  rollout_B: score = 0.1   (turn×1, no terminal)
  rollout_C: score = -0.2  (no tool call)
  rollout_D: score = 0.0   (valid tool, no terminal)

mean = (8.1 + 0.1 - 0.2 + 0.0) / 4 = 2.0
std  = 3.71

advantage_A = (8.1 - 2.0) / 3.71 = +1.64  ← 强化这条轨迹的行为
advantage_B = (0.1 - 2.0) / 3.71 = -0.51  ← 抑制这条轨迹的行为
advantage_C = (-0.2- 2.0) / 3.71 = -0.59
advantage_D = (0.0 - 2.0) / 3.71 = -0.54
Collapse 案例（v26 step 15）std=0 坍塌
4条轨迹都刷了 turn_advance：
  rollout_A: score = 0.1
  rollout_B: score = 0.1
  rollout_C: score = 0.1
  rollout_D: score = 0.1

std = 0 → advantage_A = advantage_B = ... = 0 / 0 = NaN → 0
loss = 0 → 零梯度 → 参数不更新 → 训练停止
核心代码 verl/recipe/sdpo/verl/trainer/ppo/core_algos.py : compute_grpo_outcome_advantage()

uid 是怎么分配的？

rollout_loop.py 中 if i % n == 0: uid = new_uuid()，每 group_n=4 个 step 共享一个 uid。这保证同一道题的 4 条轨迹被 compute_advantage 归为一组，做组内归一化。

⑧ Actor 参数更新 — _update_actor(batch)
这一步在做什么？
用 GRPO advantage 乘以 log_prob 得到 policy gradient loss， 反向传播更新 Qwen2.5-7B 的参数（用 FSDP 分布在 2 张 H100 上）。

advantage > 0 的动作：log_prob 被推高（模型更倾向于生成这个输出）。 advantage < 0 的动作：log_prob 被压低（模型更不倾向于生成这个输出）。
Loss 计算公式GRPO Policy Gradient
pg_loss = -mean( advantage × log_prob )

具体数字（v24 step1）：
  pg_loss = -4.94e-5  → step2: -6.68e-5  ← 在变化，说明梯度有效
  entropy = 0.52         ← 较高，模型输出多样性好
  adv range = [-6.17, +3.45]  ← 组内有真实分差

为什么 val success_rate=0 但训练中有成功？

训练用 temperature=1.5，val 用 temperature=0.4（更确定性）。模型当前学到的"策略"是以高温下随机碰运气得到正确调用，低温下就退化成永远刷 Task Completed。这说明学到的不是真正的工具调用能力，只是噪声。
